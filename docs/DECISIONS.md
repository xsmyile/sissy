# Settled decisions

Why Sissy is the way it is, and the measurement that settled each one.

These lived in [`AGENTS.md`](../AGENTS.md) until every session was paying ~29k
tokens to carry all of them at once. That file still states every rule, one line
each, and links here for the reasoning. **A dated measurement cannot become
false, only irrelevant** — most of what follows describes something that was
tried, measured and removed, so read the entry before changing what it covers.

## A permission is asked for when the user switches on the module that needs it, never at launch.

Sissy's first run asks for nothing, and the README says so out loud; that is the reason someone installs a menu bar app that reads their session logs. A module that is off must not exist as far as the system is concerned — no TCC prompt, no notification authorization, no power assertion, no entitlement that only it needs. The claude.ai login is the worked example, now that the Claude Code limits toggle it used to sit beside is gone: `VendorLoginWindow` opens only from the button, never from a poll or a launch, which is what keeps the one window a user ever sees tied to the gesture that asked for it. It replaced an import that read Claude.app's Safe Storage key — one dialog, on the click — and #167 took that out rather than keeping both: two ways to acquire a session is the third mechanism the issue exists to prevent, and the one that could not name the account it had imported. On the first: a read that could raise the keychain's own panel happens when the user asks for something, not at boot — and that is enforced, not merely intended. **The item that needs it is Sissy's own, and no longer Claude Code's.** The CLI's credential is read by `ClaudeCodeCredentials` — its file, falling back to `/usr/bin/security`, which is on that item's ACL where Sissy is not — so nothing on that path asks macOS for anything, and `ClaudeLimitsProbe` accordingly carries no `userInitiated` and no interactive read to spend it on. What remains is `ClaudeWebSessionStore`, reading the session Sissy filed itself: silent while the signature that wrote it still matches, and not silent after a re-sign. That read takes **three** suppressors, not two: an `LAContext` with `interactionNotAllowed` and the runtime-resolved `kSecUseAuthenticationUIFail` travel on the query, and neither touches the legacy keychain's own Allow/Deny panel — measured on macOS 27, a read carrying both still raised it at launch. `SecKeychainSetUserInteractionAllowed(false)` is what closes that door; it is process-wide and deprecated with no replacement, so `ClaudeCredentialsStore.suppressingInteraction` resolves it by name, throws it around the call alone and restores it in a `defer` — **under a lock with a budget on it**. The restore has no state to go back to (the API has no getter) so it restores to `true`, which is right for one reader and wrong for two: A suppressing, B suppressing, A restoring, then B reading is a scheduled read running with the panel allowed. Two readers is the ordinary case, not a corner — one `ClaudeWebSource` per linked claude.ai session, one `CodexUsageSource` per linked OpenAI account (#192). **The budget is the other half and it is not a detail**: the same call is why `loadOffPool` exists, because it blocks for as long as macOS takes to authorize and suppression is not guaranteed to stop that — `setUserInteractionAllowed` answers false where `dlsym` cannot resolve a deprecated symbol. Held without one, a single reader parked that way would take every other account's poll loop with it for good, since neither the session store nor `CodexAccountStore` goes through `loadOffPool`. A reader that cannot get in answers `errSecInteractionNotAllowed` rather than reading unsuppressed, which `classify` reads as `.interactionRequired` for both kinds of caller: the item is there, this read could not have it, the next poll tries again. A read suppressed that way answers `errSecAuthFailed` — the *same* status a user clicking Deny produces — so the status alone cannot say which happened and `ClaudeCredentialsStore.classify` takes `allowingInteraction` to decide. Such a read answers `.interactionRequired`, which must never be folded into `.denied`: nobody was asked, so the reader stays alive and the limits stay hidden until the grant returns or the user asks again. `ProviderLimitsState` and the panel's notice row make that loss visible and recoverable in a click. **A reader that cannot raise a dialog must not carry the machinery for one**: the probe's did nothing for a build, and its own comments went on promising a prompt the injected read could not produce (#183).

## Nothing Sissy does to the machine outlives Sissy.

Sissy counts while it is running and stops when it quits; the numbers live in files that are there either way, so a relaunch resumes from persisted offsets and loses nothing. `KeepAwake` is the worked example: the mode persists in `server.json`, the power assertions do not. A hold nobody can see, on a Mac whose menu bar has no Sissy in it, is a battery complaint with no path back to its cause. "Start at login" is therefore the switch that keeps a day complete, and the reason `LegacyAgentRetirement` claims the app's login item on behalf of a user whose counting used to come from the agent, rather than just unregistering it. The mode is `off`, `auto` — held while Sissy can see agents working, which is the one thing a generic `caffeinate` cannot do — or `on`, and only `on` carries a ceiling: `auto` is already bounded by its idle window, and cutting a hold out from under agents that are demonstrably still working is the failure the mode exists to prevent. A manual hold that reaches its ceiling switches itself off rather than going quiet, because "on and holding nothing" already means power management refused the assertion. The hold covers the screen as well as the system by default — a lit screen is a Mac that never locks itself, which is why it hangs off an explicit click and not a default, and why `keepScreenAwake` exists to drop that half for a Mac left running agents unattended. The system assertion is the hold and the screen one is an addition to it, never a substitute: taken alone, a screen blanked by hand would let the Mac idle to sleep under a switch the user left on. What it deliberately cannot do is keep a closed lid working: that needs `pmset disablesleep`, which is root-only and a system-wide setting that survives a crash, a `kill -9` and a reboot — the exact thing this rule forbids. Clamshell on power with an external display is macOS's own feature and needs nothing from Sissy. **The session hook is the one declared exception, and it is not the archive's.** The archive's exception is Sissy's own data in Sissy's own directory, removable by a button in Settings; this one writes a line into `~/.claude/settings.json` and `~/.codex/hooks.json`, which belong to other programs. It earns the exception the only way it can: it is off by default, the ⓘ beside the switch says exactly what will be written before it is flipped, Settings' Files row names both files, and switching it off takes both lines, the script and the inbox back out. What it cannot promise is *when* the lines come out, only that they do: a configuration Sissy could not rewrite leaves `agentHooksRemovalPending` set in `server.json` — written before either file is touched, so a crash mid-removal counts — and the next launch goes back for it, under a switch that is already off. Settings says so and offers the retry. What it cannot promise at all is the uninstall order. A user who drags Sissy to the Trash without switching it off first leaves two lines that go on forking `/bin/sh` at every session, because the script they name sits in Sissy's own folder rather than in the bundle that was trashed. Remove that folder and they find nothing, drain stdin and exit 0 — inert, but still present, in a file they did not write. That is stated in the switch's own copy rather than only here, because it is the part no code of Sissy's can undo. Nothing else may follow it out of this rule without the same four answers and the same admission.

## The archive is the one thing Sissy keeps, and it keeps it on terms.

`UsageHistory` writes a day-by-model record under `history/` because the day buckets retain two days and the CLIs' own logs are not a record anyone can count on — that is what the panel's week, the export and every per-period question are read from. It is the exception to the rule above, so it carries the conditions that rule exists to protect: its location is named in Settings' Files row, a button deletes it outright, `historyRetentionDays` bounds it, and `0` switches it off. A day is written whole, never appended to, so a cold scan that re-derives it replaces rather than doubles it — but only by a reading **at least as complete** as the one on disk, which is two tests and a reading has to pass both: every **model** at the model's own total, and every row that **names a project** at its own key. Neither alone is enough — the model total alone lets a scan that lost one project's session log pass by outspending it on another, and the row key alone freezes a day whose no-project rows a re-scan has since resolved, since attributing usage is knowing more about it rather than losing it. A day file this build cannot decode is left alone on the same grounds. A day the tail cannot vouch for is left unwritten rather than written short, which is what a relaunch whose offsets are past events the archive never saw produces. **The archive is a projection of the snapshot, never its own resume source**: `UsageStateSnapshot.historyResume` carries the per-model split beside the day totals the snapshot already held, so a resumed day continues at the byte the offsets name and the day file is rewritten whole from there. That is what makes the two writes independent — either can be throttled out or fail on its own, in either order, and the next flush reconciles the file rather than continuing it. Retention is the **engine's**, not the tail's: a provider switched off is never built, and the days it recorded are still bound by what the setting promises. Nothing else Sissy does may follow the archive out of this rule without the same four answers.

## The archive is filled in once from what the CLIs already logged, by a second pass with a cutoff of its own.

Sissy's archive starts the day it first runs and the CLIs' logs go back months, so a new install is at day zero forever — measured 2026-09-15, the widest window read $2,103 against $4,615 of logs, 53% of it older than the archive. `ArchiveBackfill` is the answer, and it is a second *mechanism* rather than a wider `retainDays`: raising that would grow the live ledger, the day buckets and the snapshot permanently, on every relaunch, to buy a one-time catch-up, and `snapshot.retainDays` would discard both providers' offsets on the way. It is **the same tail and the same adapters** — a `LocalUsageProvider` built with a `backfill` range instead of a rolling window — because the rules that make a metered day land on `ccusage` exactly are the tail's, and a second scanner would be the two readers #68 collapsed, again. The window **ends where the tail's begins**, so the two never write the same day and no coverage check has to arbitrate between them; the day it ends on is the one the tail's rolling window cuts in half and therefore suppresses, which is the only way that day is ever written at all. It **begins at the retention cutoff**, in calendar days rather than as a rolling multiple of 24 hours: a rolling bound sits a day further back, writes a day the next prune deletes, and cuts its own oldest day in half for the reason the tail's does. A day is flushed only once it is **proved** complete — files come newest first, so after one of mtime `M` no unread file can carry a later event and every day after `M`'s is final — which is what fills the panel's windows in while the pass runs *and* what stops an interruption from freezing a day it had read half of, since `isCoveredBy` would refuse to repair that one on a machine where a worktree has since been deleted. A day holding a model no rate covers is **left out rather than written short**, which only a backfill may do: the tail meters a day that is still running, and `applyPriceCatalog` prices from the refresh onwards without repricing what it already counted, so the same refusal there would keep today out of the archive for the whole of it. Nothing is persisted but day files — no snapshot, so the tail resumes from the byte it left off at whether a pass ran or not — and the record of what has been covered is `history-backfill.json`, deliberately **neither** inside `history/`, where deleting the archive would have the next launch re-deriving what the user just asked Sissy to forget, **nor** in `server.json`, whose writes a detached task would race. **The record narrows the next window rather than suppressing it**, and it carries both ends: a record of where a pass *started* cannot tell a day that has merely rolled over from a Mac that was off for a fortnight, which left the feature working exactly once — the tail's 48 h could not reach those days, the record said the window was covered, and nothing ever went back. What the archive is complete through is the later of what a pass covered and how far the tail was running, and the tail's reach is the snapshot file's own mtime rather than the `savedAt` inside it, which is a stat against a parse of 645 KB. So a plain relaunch reads nothing, a fortnight off reads a fortnight, and widening retention reads the whole window again. Deleting the archive ends a pass in flight and records the window as covered, because a pass is a second writer the aggregator's `forgetArchivedDays` does not reach — cancelling alone is not enough, since cancellation is observed between files. Measured on one machine: 419 Claude files and 424 Codex rollouts, ~870 MB, 73 s in a Debug build, and the archive it wrote agrees with `ccusage` **to the token on all four counts across 70 days**, both providers, with the whole cost within $0.00008 — the `pricing-oracle` job asserts that on a dated fixture, which `--scan` structurally cannot, since it runs the tail's own window and reports today.

## A project is a repository, not a directory.

`ProjectResolver` walks up from the `cwd` a log line names to the first `.git`, and a `.git` *file* means a worktree whose `gitdir:` pointer names `<main>/.git/worktrees/<name>` — so the work counts against `<main>`. Without that one repository reads as several rows that each look small: measured on a real day, 44 distinct working directories resolve to 31 projects, and `sissy` only adds up to its real figure once its worktrees fold into it. `legion/frontend` is not its own project either. Two unrelated repositories sharing a basename render the same label and are told apart by the path in the tooltip — the accepted cost of a row named the way the user names it. **A walk that names no repository answers nothing**, and the usage is counted without a row rather than given one named after a path Sissy cannot verify: a CLI's per-conversation scratch directory is not a project, and neither is a deleted worktree, whose money belonged to the checkout it was cut from. The walk never stats the starting directory, so a worktree kept *inside* its repository still resolves once deleted. One kept beside it has nothing left to walk up to, which is why **a checkout a `.git` entry has been read from is remembered**, and why what remembers it is `ProjectLedger` rather than the tail's snapshot: it holds no token math, so a `UsageStateSnapshot` schema bump must not take it — that bump quarantines the file and forces the cold scan that needs the memory most, and it has happened seven times on one machine. It is **one ledger for every provider**, because two answer the same deleted path differently as soon as one has seen it alive: as a memory per adapter, Codex's held nothing at all, none of the directories its own rollouts name being a repository. `projectCheckouts` stays on the snapshot read-only, so an install that predates the ledger hands its memory over once. **The ledger learns from git, not only from the lines it reads**: landing on a repository reads the worktree list git keeps in `<repo>/.git/worktrees/*/gitdir`, at launch and on the tail's own cadence, so a worktree is written down while it is alive instead of looked for once it is gone. Without that, learning is a race against `git worktree remove` that the tail loses whenever it is not running — measured 2026-09-13, a cold read of that day's logs could name 66% of its tokens and the day before 21%, every missing one belonging to a worktree already deleted. What none of this can answer for is a checkout created *and* deleted while Sissy was not running: git has pruned its side, the logs name the path and nothing else, and there is no reading left to remember — **unless the session wrote it down itself**. That is the `checkout-inbox`, fed by the `SessionStart` hook `AgentHookInstaller` registers with both CLIs when the user switches it on, and it is the only evidence that does not require Sissy to have been running. `session-start.sh` reproduces the walk exactly: `--show-toplevel` for the checkout, the common dir minus `/.git` for the repository, a submodule answering itself. Two guards are not optional and were both measured: an inherited `GIT_DIR` beats `git -C` and answers for a repository the session was never in, so the environment is stripped; and `core.worktree` lets a repository name any path on the machine as its own checkout, so the toplevel must be the directory the session started in or an ancestor of it — which is the invariant the walk gets for free. The inbox is foreign input and is read as a boundary: `O_NOFOLLOW`, a regular file this user owns, size-capped, two absolute lines, and `adopt`ed rather than `remember`ed so what Sissy saw itself always outranks what it was told. An entry is consumed on read, which is what bounds the directory. What is still unanswerable is a checkout created and deleted while *neither* Sissy nor a session was there. Remembering a reading is not inventing one: nothing remembers a directory no `.git` was ever read from, so a CLI's scratch directory stays nameless however often it is seen. A directory still on disk is answered by the disk, because an emptied directory is a change in what a path means where a deleted one is the end of it. Without this, attribution is a property of when Sissy happened to read the line rather than of the work — measured 2026-09-13, the live tail named 99.7% of one real day and a cold re-read of the same day after its worktrees were deleted named 34%; across the whole history 23.3% of tokens no longer resolve, and 50.8% of September's, the month ephemeral worktrees became how the work is done. That is also what stops a cold scan from *degrading* a day the live tail attributed correctly, since a row it can no longer name goes unattributed instead of moving the money to a dead path. **A project path a persisted row carries is read through the resolver again before it is used**, never migrated on disk: the archive keeps the directory it saw, and what that path *means* is today's answer — for a checkout that is gone, the repository the remembered reading named; for a path no reading ever verified, nothing at all, so a row an older build wrote for a scratch directory stops claiming one. Two rows that answer the same key sum rather than replace. Rewriting the file instead would destroy the attribution of a repository on an unmounted disk the first time it is read without it, where a projection answers from the checkout it remembers and is whole either way. It is also what lifts the freeze the coverage check would otherwise hold such a day in forever. **A project path is personal data** — a client's name is a directory's name. The panel renders the last component only, the archive holds the path, and anything that carries it off the machine has to say so. `UsageHistoryExport` is the one thing that does: it writes both the label and the path, because a pivot table that groups on the label alone sums two repositories sharing a basename into one row, and the button that writes it names what the rows carry before it is pressed rather than after.

## Two counters ride the tail, and they are two questions rather than one.

A *session* is a CLI somebody started; an *agent* is a sub-agent that session spawned. Measured 2026-09-18 over 30 days of `~/.claude/projects`, 442 sessions spawned 189 agents — one number says how often the user sat down, the other how much of the work was delegated, and their sum says neither. Counting them costs **nothing extra to read**: every `Agent` block rides an assistant line that already carries `message.usage` (189 of 189 measured), and Codex's `session_meta` is already a prefilter term and already parsed for the `cwd`, so the counts come off the one JSON parse the line was billed from — which is why `SourceAdapter.event(from:seen:activity:)` takes an `inout` accumulator rather than gaining a second call. Three things are settled. **The names have changed and the old ones still count**: the Claude tool is `Agent` and was `Task`, and a reader that knows only the current name reports zero for every day it can still see. **Codex says "another thread opened this" three ways** — `source.subagent.thread_spawn` (26 rollouts), `source.subagent: "review"` (119) and `thread_source` alone (58) — and that is deliberately *not* `namesAParentSession`, which decides whether a rollout replays its parent's turns and must stay narrow: a `review` rollout's first `token_count` lands 0.09 s after its `session_meta` and is a real turn, so widening that gate would take 119 genuine turns off the day. **And a Codex rollout is keyed by its file, because its payload names its parent**: a spawned rollout's `session_id` *and* `id` both carry the thread that spawned it, so a ledger keyed on either finds the parent's key already claimed and drops every agent — measured, all 8 of that day's, silently, against a unit test that passed because its fixture had been given an id of its own. Idempotence is the archive's own: a count lands in a day bucket the archive writes *whole*, so a cold scan replaces rather than doubles, and `UsageHistoryDay.merging(counts:)` keeps whichever reading counted more, because a count can only ever be under-observed. The counts ride `historyResume` for the reason the per-model rows do — the offsets resume at EOF, so the lines they were read from are lines nothing will read again — and `ArchiveBackfill`'s record carries a version that a new counter bumps, since a record saying the window is covered is what would otherwise leave every day before the upgrade with tokens and no count.

## How long a day was worked is a reading of the same turns, and it is minutes rather than a span.

The turn's timestamp is already on `UsageEvent`, so `AgentActivityDay` costs nothing new to read. Three things about it are settled and measured. **The span from a day's first turn to its last is useless** — measured 2026-09-19 over 12 days of `~/.claude/projects`, it reads 23h59 on two of them, because one long agent run straddles the night — so the reading is the minutes covered by *blocks*, runs of worked minutes separated by no more than `idleGapMinutes`. That threshold is a constant and not a setting because it barely matters: 10 against 15 minutes differ by 1.6% on the widest of those days and under 5% on nine of the twelve, and a switch would be asking the user to tune a number that cannot move the answer. **The day is stored as a bitmap of its own minutes, not a list of intervals**, because the tail reads files newest first and a day's turns therefore arrive out of order — a set is order-independent and idempotent, which is exactly what a day the archive rewrites whole needs, and it is what lets a cold re-scan OR the same minutes back in rather than double them. The minute is the grain the reading is *defined* at rather than a rounding: measured the same day, it lands within a median of 7 minutes of summing the exact gaps between consecutive turns, about 1% of a twelve-hour day, for 188 bytes where the instants cost 80 KB. **And a window is never the sum of its providers.** Codex runs almost entirely inside the minutes Claude Code is already working in — measured 2026-09-19, adding the two rows says 12h40 on a day the union puts at 11h15 — so `UsageHistoryRollup` unions each day's readers before summing the days, and the per-provider rows on the page legitimately add up to more than the figure above them. The delegated half is the same rule applied to the sub-agents' own turns, which is 11–28% of the day across those twelve, and it is read off `isSidechain`, the `subagents` directory a transcript came from, or the `session_meta` that opened a Codex rollout — all of them fields on the object the turn was already billed from. **What is deliberately not measured is the split between the minutes a person drove and the minutes the CLI drove itself.** It cannot be: a session a program started writes the same `user` message a person typing does, and telling them apart means reading the prompt's text, which is the most personal thing in those logs and a heuristic against one machine's tooling besides. Measured 2026-09-17 on this machine, 482 of the day's `user` lines were plain text and most were a tool asking Claude Code for a branch name; the two rules tried for it disagreed by a factor of five, 22% against 78% of the day, which is a reading that moves with its own definition rather than with the work. The strip on the page draws blocks at one intensity for a related reason: inside a block the session's turns and its sub-agents' alternate every few minutes, which across 300 pt is finer than a pixel and would draw as a moiré, so the delegated share is a clause in the caption where it can be read. The export carries it in a **second file**, `sissy-activity.csv`, one row per day and provider — a day's minutes belong to no model and no project, so a column on the usage rows would be multiplied by however many models answered that day the first time somebody pivoted on it.

## What the agents are holding is a reading of the Mac, and it needs no permission.

`AgentProcessReader` answers `KERN_PROC_ALL`, `proc_pidpath` and `proc_pid_rusage` for this user's processes: no entitlement, no TCC prompt, no hardened-runtime exception, and zero refusals across 665 processes measured 2026-09-18. **The identity is the executable's path and not its name** — Claude Code's native build installs one executable per version under `~/.local/share/claude/versions/` and names it after the version, so the kernel reports `2.1.277` and a matcher keyed on the process name finds none of six live sessions; `argv[0]` is read only for a process running under a JS interpreter, because reading it for every process costs 19.3 ms against the sweep's 1.2 ms. **Two totals, because they differ by more than the number itself**: 1.94 GB in the agents themselves against 4.88 GB with the builds and dev servers under them, measured the same day. The first is what closing a session hands back and the second is why the Mac is struggling. **The series is in memory and nowhere else**, which is the rule rather than an omission: a reading from a Mac that was asleep is not a low reading, so the sparkline starts when Sissy does and says so. It samples with the panel closed, and that does not break *a surface that is not on screen costs nothing* — that rule is about retained view graphs, and this is 1.2 ms every 15 s. The page it feeds is a page for `PanelIdentities`' reasons, and the Overview carries **one line** from it, under the providers rather than under the projects: it answers the same question the gauges do — whether there is room to keep working — on the other axis that stops work *now*, where what a period cost is asked afterwards. That line is drawn on every frame including one where nothing is running, because it is the only door to the page and a door that comes and goes with the day is not one.

## Sissy reads a repository's commit identity and never writes one.

`GitIdentityMonitor` asks git who would sign a commit in every repository `ProjectLedger` names, and the panel's `Identities` page says which of them commit under a name their forge does not expect. **The remote is the rule, and it is learned rather than configured**: an electorate whose repositories agree on a name has an expectation, and the one that disagrees is the finding. Measured 2026-09-17 across one machine's 23 live repositories, the remote classifies 23 of them where a folder root classifies 15 — the other 8 sit outside every root and are right only because the default identity happens to be theirs — and the folder cannot see the case this exists for at all, a work repository cloned anywhere and committed to under a personal name. **The electorate is the account on the forge, not the forge.** Grouping by host alone puts every organisation on `github.com` in one vote, so a user with ten personal repositories and three correctly-scoped employer ones has the three flagged for being outnumbered — a false finding against a setup that is right, which is the one failure a detector that is silent until something is wrong must not have: saying nothing costs a finding, saying the wrong thing costs the feature. **A host whose accounts all agree is the fallback, and only where it is unanimous**, which is what still catches the first repository seen under a new account while a mixed host has no unanimity to fall back on and each account answers for itself. Two repositories are the least that can agree; one, or a tie, expects nothing, or the first repository under an account would define it for every one after. An electorate is judged as a whole rather than each repository against its own neighbours, because the alternative left eight right repositories `unjudged` on the strength of one wrong one. **Nothing is written, and that is the whole reason this needs no exception to the rule above**: the correction is `git config --unset` on the clipboard, so there is no preview, no backup, no refusal of stale writes and no undo to build, and no line of Sissy's in a file it does not own. It is offered only where it would work — a repository wearing the wrong name because of a *global* rule has nothing of its own to unset. **Ask git, never reimplement git.** Identity resolves across system, XDG, global, repository and worktree config through `include` and `includeIf`, and `includeIf gitdir:` matches the **git directory**, so a worktree outside every configured root still takes its repository's identity — measured, `~/orca/workspaces/legion/penguin` commits as the work account off `~/mdev/legion/.git/worktrees/`. A reader that classified by checkout path would call all 142 of this machine's checkouts wrong to find 26 repositories. Three calls, each load-bearing: `rev-parse` proves the path is a repository, because `config` and `var` both answer from the global config with none and a deleted checkout would otherwise report the machine's default as its own; `config --show-origin --show-scope` names the file, taking the **last** match, since git lists in parse order and the first line is the one the winner overrode; and `var GIT_AUTHOR_IDENT` resolves what that identity is. **`var` is not asked whether an identity exists, because it invents one**: with no `user.email` anywhere git falls back to the gecos field and the hostname, and whether it then refuses its own guess is a property of the machine — measured 2026-09-17, a Mac whose hostname yields no domain exits 128 with `unable to auto-detect email address (got 'davide@blackbird.(none)')` where a CI runner whose hostname ends `.local` was served `Anka <runner@….local>` with status 0, an address nobody owns that would have joined its forge's electorate and could have become what that forge expects. So the configuration decides: no `user.email` in the chain is unset, whatever `var` would have answered. The environment is built rather than inherited — `GIT_DIR` beats `git -C`, `GIT_AUTHOR_EMAIL` beats every file — and `/usr/bin/git` is used only behind `xcode-select -p`, because it is a Command Line Tools shim that opens a system dialog on a Mac without them. What the reading cannot cover is `-c`, `--author` and `GIT_AUTHOR_EMAIL` at commit time, and the page says so rather than claiming the commit. **A round re-reads only a repository whose own files have moved**, and that is not an optimisation to drop: a `Process` costs about 67 ms whatever it runs — measured 2026-09-17, `/usr/bin/true` costs the same as `git var`, so it is the spawn — which put a 23-repository round at 5.82 s of a core. A reading cannot change unless a file behind it does, so the round stats the include chain `--show-origin` named plus the three a *new* `user.email` could appear in, and spends processes only where a stamp moved: measured on the same 23, 5.82 s cold and **0.01 s** at rest. **It is a page of the panel and not a tab of Settings**, because Settings holds switches — every row in it is a `LabeledContent` and there is no list in the window — where this is a reading with no lever on it, and 23 repositories at two lines each go past the 600 pt budget on the first day. The Overview carries one line and only when something is wrong: a badge per project row is the decorative signal on the cost axis this panel already refuses, since that list is ordered by spend. **The page shows the findings and folds the rest away**, which is the second half of the rule a section may be bounded under — a page one click from several times its own height, the way the status tree's collapsed groups bound 34 OpenAI components — and not the half that was removed, which was bounding a section to keep the popover on the display. Measured 2026-09-17 on 23 repositories: listing them all came to ~975 pt against the 690.5 pt of the tallest page before it, and it filled a 14" screen top to bottom; folded, the same page is 142 pt, or 217 pt with a finding on it. Collapsed it still answers the question — one sentence saying whether anything is wrong, and the count of what was read — and the repository a project row was clicked for never folds, or the click would answer about everything except the row it came from.

## Settings has a height budget, and a row shape that pays for it.

`SettingsRootView.maxContentHeight` is 600 pt: a tab that needs more scrolls, and a tab that habitually needs more is a tab that should have split. Without a ceiling the window followed its content off the bottom of the screen and there was no way back — `fixedSize` is what makes the window follow the selected tab, and it also makes it unresizable and stops the `Form` underneath from ever scrolling, since a scroll view given its own ideal height never compresses. Measured: General at 850 pt against the 841 pt a 14" Mac set to a larger text size has room for, and the 775 pt of a 1280×800 display. What buys the room is the row — every control is a `LabeledContent` whose label carries the title *and* its description, so the caption sits beside the control instead of under it as a full-width paragraph, and the platform words it as secondary rather than one point below the label. Measured on the same eight controls: a `Section` per control with a `callout` paragraph came to 779 pt of content, this shape to 471 pt. **The prose was never the problem and deleting it is not the fix** — the ⓘ popovers are where a control that reaches outside Sissy's own folder says so before it is used — what the hook switch writes, and what the export carries off the Mac — the Files row still names both files, and the keep-awake caption still carries the only two numbers in the app that say when a hold ends. **A tab is earned by a module, not by a long tab**: #38's notifications pane is a tab, a pane holding one switch is a row.

## Sissy's motion is one 24-frame sequence.

`Assets.xcassets/SissyMotion` holds a blink rendered at 60 fps as vector imagesets, and `SissyMenuBarMotion` slices it into the whole blink plus its two halves. Frames 6–9 are the byte-identical shut-eye hold, which is why the closing half stops at 6, the opening half starts at 9, and `step(at:)` reports the hold as a single frame held for all four frames' worth of time — a write to `button.image` is answered by AppKit re-capturing the whole status item into a bitmap (`NSStatusItem._updateReplicants`, measured at 34% of the app's idle main-thread work), so a frame nobody could tell from the last one is not free. `SissyMenuBarAnimator` owns `button.image` from the moment it exists — anything else assigning it drops the remaining frames of a gesture. A blink fires when a frame lands (`SissyModel.lastFrameAt`, rate-limited by `SissyMenuBarMotion.dataBlinkCooldown`, because the tail coalesces emits only down to `UsageReaderShared.pollEmitThrottle`); the halves play when the pose changes; Reduce Motion, an open menu, or the pose the app launches in snap instead. **Two surfaces play Sissy**, and they are separate implementations because one assigns an `NSImage` and the other is SwiftUI: the status button through `SissyMenuBarAnimator`, and the panel header through `Panel/PanelSissy.swift`, which blinks on the same arrivals so an open popover is not a still Sissy. What they must not each reinvent is the timing — `SissyMenuBarMotion.step(at:)` is the single source of which frame a running gesture is on, and `dataBlinkCooldown` of when the next one is due. The panel plays only the blink: the poses still cross-fade there, since a 24 pt SwiftUI `Image` swap has no menu bar to match. There is no idle animation and no gesture on the cost axis: motion reports arrival, not spend. The frames are derived art — regenerating them needs the motion geometry that lives outside this repo, so a re-traced silhouette means re-rendering all 24.

## A row answers for itself in a menu, and a block too long for a row answers in a page of the panel.

Two surfaces used to answer in a nested `.popover` — `ProjectRowView` and the status block's service tree — and as of 0.1.10 neither does. Apple's guidance rules it out in one line: *"Never show a cascade or hierarchy of popovers, in which one emerges from another"* (Human Interface Guidelines, Popovers). The cost of ignoring it was measured, 2026-09-17 on macOS 27 against a harness reproducing `UsagePanelController` exactly: dismissing a popover presented from inside the panel leaves the panel's own window with its new size committed to the window server and its **new origin not**, for ~555 ms. Cocoa origins are bottom-left, so for that half second the panel held its bottom edge and moved its top, drawing itself displaced by exactly the height difference between the page it left and the page it arrived at — down when the destination is taller, up when shorter, and the header off the top of the screen either way. `NSWindow.frame` was correct throughout, so nothing in this app's layout could see it or fix it, and every remedy measured failed: `animates = false`, resetting `backingType`, `disableScreenUpdatesUntilFlush()`, `setFrame(_:display: true)` with `invalidateShadow()`, nudging the origin, resetting `positioningRect`, and deferring the resize by 16, 50, 120, 250, 300, 350, 400 or 500 ms — the freeze ends at a fixed moment whatever happens in between, so a later resize is simply wrong for less of it. Not resizing inside that window is the only thing that works, and a surface that is not a popover never opens it. So the tree is a page (`UsagePanelView.Page.services`, one level in from the vendor's own), which also answers the complaint the card was invented for better than the card did: nothing below it can be pushed, because there is nothing below it. And the repository's row carries the **forge's mark after its name, and the mark is the link**: it costs the row no height, a row without one is saying there is nothing to open, and a mark placed *before* the name would start every repository's name one step right of every other row's — which is the rule the bars were given a line of their own to keep. A pull-down `Menu` was tried in between and dropped: it opened over the rows below it, which is a lot of a 340 pt panel spent on two items, and macOS draws no icon in a SwiftUI menu item, so the mark had nowhere to be inside one. The two actions — the page, and the path on the clipboard — sit on the **right-click**, which is where the same guidance puts them: *"a context menu lets people access a small number of frequently used actions relevant to their current view or task"*. A menu is the system's own mechanism rather than a window of Sissy's, so it cannot resize the panel and does not dismiss the popover it opens over, measured on macOS 27. The hover stays the tooltip's, which is the only place a path is readable, and a path the pointer could select is what this gives up — so it goes where selecting it was heading, the clipboard. What neither surface may ever be is the only way to something: the repository's own name stays on the row and its path stays in the tooltip. The page it offers is **read rather than guessed**: `ProjectResolver.remote(ofRemoteURL:)` keeps a remote a browser can already open exactly as it is, port and all, and composes `https://<host>/<path>` only where the host is the whole address — an `ssh` remote naming a port is pointing at a transport, `ssh.github.com` on 443 serves no page, and that row keeps its repository with no way out to it. **A list that folds has a page, and its label is the door.** The project list keeps five rows and folds the rest, which is a reading with nowhere to go, so `UsagePanelView.Page.projects` holds the whole of it — from the Overview across every provider, and from a vendor's own page for that vendor alone. The door is the section's **label** rather than the folded row: the fold exists only past five repositories, so a door on it comes and goes with the day. The fold keeps its figures, and the label carries the count instead of a bare chevron, because a chevron says there is somewhere to go without saying what is there. **Every row in the section is a repository, which is what lets that label count them.** What named none used to be the last row of it — under a label counting projects, ranked among them, with a bar to be compared by and a hover where the others keep a path — and as of 0.1.11 it is a line at the foot of the page instead, which is the one surface that has to close the arithmetic anyway. The figure is not dropped, only moved: `UsagePanelSnapshot.ProjectsResidue` carries it, and on the combined page it also carries which CLI lost the attribution, one mark where a single CLI did and a figure each where both did — the one reading a provider's own page structurally cannot give, since it shows its own residue and nothing there says how the two compare. **And the section draws a row's share behind the row rather than under it.** A bar of its own doubles a row's height, which is what a folded five-row block can least afford, so `ProjectRowView.BarPlacement.behind` washes the same share across the row's own band: track, fill and `BarGeometry.fillWidth` unchanged, so a repository worth a fraction of a percent still draws the stub it always did. Measured 2026-09-19, a four-row section went from 178 pt to 140 pt. The page keeps `.under`, because there the bar carries the per-provider split in its segments and the page has the height to spend. The page carries no period control: the rows come from the day buckets, and what a project cost over a month is #81, closed, which the export already answers. **The provider rides on the row, not on a column or a filter**: a repository worked on through both CLIs is one row by design, so which CLI spent is a property of that row's money — the marks after the name say who, at `PanelMetrics.markSize` rather than the forge mark's size beside them, and `ShareBar`'s segments say how much of each, neither costing the list a line or a legend.

## The panel's ceiling is the screen it opens on, and no section pays for it.

`UsagePanelController` reads `button.window?.screen` per showing and hands `PanelMetrics.maxHeight(on:)` to the panel, which measures its header and its page and gives the page's scroll view the smaller of its own height and what is left. A page that fits is untouched — the scroll view is set to the page's measured height and scrolling is disabled — so the popover is the size it has always been. This replaced a ceiling on the project list, which was the wrong trade: measured 2026-09-15, `visibleFrame` is about 957 pt on a 14" built-in and 1415 pt on a 2560×1440 external against a tallest-page reading of 690.5 pt, so the section was hiding repositories to fit a screen nobody was in front of. Bounding a section is for keeping what is *below* it reachable, or a page from being one click away from several times its own height — the second is what `StatusTreeGeometry` still does for 34 OpenAI components — never for keeping the popover on the display. **Two mechanics here are measured and not guessable.** A `ScrollView` is greedy: given a flexible proposal it takes all of it, so `.frame(maxHeight:)` on the panel, `.fixedSize` on the scroll view and both together all report the full ceiling for a 100 pt page. Only an explicit height on the scroll view works, which is why the ceiling cannot be expressed on the panel as a whole — the greedy child is what it would be clamping. And a height measured with `onGeometryChange` is not available to the layout pass that produced it: the first `sizeThatFits` answers with the header alone, so the controller lays the host out before `show`, or the popover opens as a 45 pt stub and jumps.

## The divergence is a version, not a package manager.

npm no longer ships the JS implementation: at 20.0.20 the `ccusage` package is a launcher whose `src/cli.js` spawns `@ccusage/ccusage-<platform>`, a native binary of the Rust rewrite — verified 2026-09-12 (`file` reports Mach-O arm64). So "the npm JS build" and "the Homebrew Rust build" are no longer two implementations to choose between, and the old framing of this rule was wrong. What is real is the **stale pin**: measured on 1M `ephemeral_1h` opus tokens, build **20.1.0** bills the 1-hour tier at the 5-minute rate and says $6.25 where Sissy says $10.00 (2026-07-29 and 2026-09-10), and **20.0.20 says $10.00**, agreeing with Sissy (re-measured 2026-09-12). Claude Code writes ~93% of its cache at the 1h TTL, so a 20.1.0 reading looks like Sissy over-billing by ~7% — it is not. The trap that keeps 20.1.0 alive is Homebrew's: the project moved from `ryoppippi/ccusage` to `ccusage/ccusage` and renumbered *backwards*, so `brew outdated` sorts 20.1.0 above 20.0.20, stays silent forever, and `brew upgrade` is a no-op — only `brew uninstall ccusage` and a fresh install move it. Before acting on a user-reported gap, get their `ccusage --version`; About → **Copy diagnostics** also names the install (`CcusageProbe`, which classifies it by where its symlinks land — `node_modules` is npm, `Cellar` is Homebrew).

## A repeated assistant line is a turn still streaming, not a duplicate to drop.

Claude Code writes the same `requestId` two to four times as an answer streams: `output_tokens` grows with each copy while the input and cache counts, fixed when the request was made, repeat unchanged. `ClaudeCodeAdapter` therefore bills a repeat as the **difference** in output and nothing else — `SeenEvent.billedOutputTokens` is what the dedup ledger carries for it, and `UsageStateSnapshot.DedupKey.outputTokens` is why a turn whose copies land either side of a relaunch is still billed once and whole. Measured 2026-09-12 on 2026-09-11: keeping the first copy gave opus 2 751 478 output tokens against ccusage's 2 872 151 and the day $3.97 short, while keeping the last lands on **all four token counts exactly** for both models and the day within $0.000022 of $598.854905. This replaces an earlier note claiming a ~0.35% residual localized to `isSidechain` sub-agent entries: sidechains had nothing to do with it, dedup policy had nothing to do with it either — deduping by `requestId`, by `message.id`, by the pair, per file or across the tree all give the same number. The oracle fixture carries a four-copy turn for this reason; a fixture of one line per request id bills the same either way, which is how the bug shipped past it.

## The plan comes from a different place for each provider, and in neither case the obvious one.

Codex names it on the same `rate_limits` block as its windows (`plan_type`), so `captureWindows` takes both and `codexResume.plan` persists it for the same reason it persists the windows. That source answers only while there are unread bytes, though — a reader resuming with its offsets at EOF has nothing left to re-read and the row sat without a badge until the user's next turn, so `CodexAuthSource` reads the `chatgpt_plan_type` claim out of the id_token in `~/.codex/auth.json` at boot and any rollout event then overwrites it. That file also holds Codex's tokens: the access credential is what `CodexAuth.credential(at:)` exists to hand the usage reader, the **refresh** token is dropped on the way out — a Codex Sissy did not sign in is one Sissy may not renew, the token being one-time —  and the JWT's signature is deliberately not verified — the value is a display string read from the user's own disk. Claude Code publishes it nowhere Sissy already looked: the OAuth usage endpoint carries buckets and no plan (measured), and the credential itself names a `subscriptionType` but not the organisation the seat belongs to, which is the half the badge needs. `ClaudeProfileSource` therefore reads `oauthAccount.organizationType` out of the CLI's own profile file — `<home>/.config.json` where the CLI has migrated to it, `<home>/.claude.json` otherwise, and `$HOME/.claude.json` for the default home, where the CLI keeps the profile *beside* the config directory rather than in it. `ProviderHome.claudeProfileURL` is the resolution and `ServerConfig.providerHome` supplies the home, derived from `claudeDataDir` rather than from the environment, because a user who pointed that somewhere else meant it and strips the `claude_` prefix, which lands exactly on the token Claude Code's own label switch takes. **That prefix is namespacing rather than part of the token, so every reader strips it before the app sees it.** `ClaudeAccountIdentity.plan`/`planTier` and `ClaudeWebOrganization.plan` answer in the vocabulary `ClaudeProfileSource` publishes, off one normaliser rather than three; passing an archived identity's raw tokens through instead labelled every account but the signed-in one "Claude Team", metered at "Default Claude Max 5x". Alongside the plan it reads `userRateLimitTier` as `planTier` (`max_5x`), which the app folds into the badge only when the tier names the plan it decorates: a Max account reads "Max 5x", while a Team seat metered at the same tier keeps "Team" and puts the tier in the row's tooltip, because "Team 5x" is a plan nobody sells. **The seat comes from a third place again, and from two of them.** Measured 2026-09-16, `api/oauth/profile` carries `organization.seat_tier` and claude.ai carries `seat_tier` on the *membership*, both `team_tier_1` for one account — so the membership is picked before the organisation is taken off it, since reading the organisations alone cannot say which seat belongs to the one chosen and an account holding two would wear the other's. `ClaudeAccountIdentity.seat` carries it, which is what lets an account Sissy knows from either source badge "Team Premium" rather than "Team" — it read neither until then, so every row but the CLI's own was a plan short. **An archived identity is frozen at the build that filed it, so a link outranks it.** `captureActive` reads only the active slot and only on a token it has not filed, and an archived access token expires with no refresh Sissy is allowed to spend — so a non-active account cannot be re-identified at all, and its link is the one identity that can still move. Measured the same day: an account archived before `seat` existed kept badging "Team" beside a live "Team Premium", and would have kept it through a fresh link. Downstream of that, a row resolves **one** account rather than ordering field by field — the reading's, and the archive only where there is no reading at all — which is safe precisely because the reading is already attributed to the row it is on. Every token reaches the app raw and lowercase; `UsageFormat.plan(_:tier:)` is what words them, so a tier a vendor ships tomorrow needs no release. Neither *file* is fresh on demand: Claude's updates when the CLI re-fetches its profile, and Codex's id_token is restamped only when the CLI renews it. What answers on demand is Codex's usage endpoint, which names the plan beside the windows, so that badge is one poll behind rather than one turn. Claude's does not: `ClaudeLimitsProbe` carries no plan at all, which is why the profile and the account registry stay its only sources. **That same file answers for the credits, and it is a record rather than a reading.** `cachedUsageUtilization` in `.claude.json` is the usage endpoint's own reply, cached by the CLI — the identical payload `ClaudeLimitsProbe` authenticates for, `spend` block and all — so the number someone opens the browser for is readable with no prompt, no network and no grant to lapse. **What it is not is current, and it cannot be made current.** Measured 2026-09-14: the CLI rewrote `.claude.json` ten seconds before the reading and `fetchedAtMs` had not moved in 59 minutes of continuous Claude Code use, because only `/usage` refreshes it. Against the live reply at that moment it named 19 260 credits spent where the account had spent 26 275, under a cap it did not know had been raised from 25 000 to 30 000. So it is the fallback when nothing better is running and never an argument against a live source — an earlier version of this note had it the other way round and was wrong. Hence the reading carries the vendor's `fetchedAtMs` and the panel prints it: a spend shown without its age is a claim of being live that this source cannot make. The money stays in minor units with the vendor's own currency and exponent all the way to the formatter, and never meets `ProviderSlice.cost`: one is what was charged, the other Sissy's estimate of what was metered, and summing them would be inventing a third number. **And it answers for an account that is not necessarily the one signed in.** Only Claude Code writes that file, so a switch Sissy makes reaches the keychain at once and `.claude.json` not at all — measured 2026-09-16, a switch at 16:26:53 left a file rewritten at 16:29:31 whose `oauthAccount` had been fetched at 12:28:10 and had not moved, so the row carried one account's id under the previous account's name, email and seat, and switching again could never change it. The file names its own owner and Sissy reads it: `oauthAccount.accountUuid` and `cachedUsageUtilization.accountUuid`, **two stamps rather than one**, because the blocks are written at different moments and legitimately disagree — a running `claude` holds its identity in memory, so that same day's usage cache was refreshed 39 s *after* the switch and still stamped with the account it had started as. `ClaudeCodeSignals.attributed` therefore judges each half against the registry's active account: an identity that contradicts it gives way to the registry's, credits that contradict it come off the row, and agreement keeps the file whole, because it is the richer reading and the only one that names the seat. Unknown on either side is not a contradiction — an older CLI writes no `accountUuid`, and a registry that has identified nobody claims no active account — and the reading stands as it always has. The registry can lag too, by its 120 s poll and indefinitely while `identify` is offline, and it is still the authority here: the row is keyed by `activeUUID`, so pairing it with that account's own identity is one account per row, which is the invariant, where the file's was two. **And where the registry names nobody, the file's own stamp is the active account.** The registry names nobody whenever it has never identified a credential — offline at launch, a keychain that would not answer, an engine built without one — and that state used to stand every judgement down: a lone claude.ai session was laid over the row whoever it belonged to, and a `cachedUsageUtilization` stamped with another account was kept. `ClaudeCodeSignals.activeAccount` is the one answer all three readers take, so a name is available wherever one exists. The exception that survives is a Mac nothing names at all, where a lone session is the only answer there is.

## A credits reading is the vendor's own figure in the vendor's own unit, and three absences are not zero.

Anthropic bills a spend against a cap in the account's currency; OpenAI writes a credit *balance* on the same `rate_limits` block Sissy already parses for the windows and the plan, names no currency for it and sends `individual_limit: null` — measured 2026-09-16, on all 10 306 blocks on one machine. So `ProviderCredits` carries a `CreditsUnit` and every figure on it is optional: a source answers for what it can and says nothing about the rest, and folding those together invents a number. **What this buys Codex is a line, not a gauge** — with no ceiling a bar would be picking a denominator the vendor did not give, which is the one thing this row exists not to do, so `CreditsRow.fraction` is optional and the bar goes with it. The two ways the reading goes missing are two different facts and neither is zero: the key is absent on a Codex older than 2026-05-18 (6 801 blocks), and `balance` is null where the CLI has the key and not the figure (23). **Neither flag beside it is read, and the omissions are the same rule read from both ends.** `unlimited` suppressed the whole reading for one build, which was inventing an absence: it only means an *absent* balance is not worth reporting as missing, and a balance that does not parse already answers nil on its own — CodexBar reaches the same place from its own measurements, keeping a finite balance or cap reported alongside the flag and dropping only the reading that names neither. `has_credits` is deliberately **not** read as `isEnabled` — it reports whether a finite pool exists, and `has_credits: false` beside `balance: "0"` is the ordinary reading on an account that never bought any, which is 3 482 blocks here and the confirmed zero the row prints. The balance arrives as *text*, so it is shape-checked before parsing and read against `en_US_POSIX`: `Decimal(string:)` takes the machine's separator and answers with however far it understood, which on this Mac turns `"12.5"` into `12` and `"12 credits"` into `12`. It rides `codexResume` for the reason the plan does — with offsets at EOF there is nothing left to re-read and the section would be missing until the CLI's next turn. What is still Claude's alone is the hidden zero: a spend of nothing against no cap gets no row, because that is most accounts and a permanent "Not enabled" under every provider page is a row that never changes.

## A vendor's status is read from the vendor, dated by Sissy, and never inferred.

`ProviderStatusMonitor` polls each metering vendor's public status page so "is it me or them" costs no browser tab. Four things about it are settled and measured. **The age on the row is Sissy's own fetch time**, never the feed's `updated_at` — measured 2026-09-15, OpenAI's read `2026-07-09`, two months stale, because it moves on incidents rather than on polls; a row dated from the payload tells a healthy provider it has not been heard from since July. **A failed fetch publishes nothing**, so the last reading keeps its own age and the age growing is the signal; a feed that has never answered says `unknown`, which is never an outage, because a page Sissy could not reach is not an incident. **The sentence is one shape and the tree is two.** Both vendors answer Statuspage v2 at `api/v2/status.json`, so the row has one reader; the services under it do not. Measured the same day, OpenAI's Statuspage-emulated `summary.json` answered 25 flat components where its own page carries 34 in 5 groups — it drops eight, `Chat Completions`, `Responses`, `Conversations`, `GPTs`, `Image Generation`, `ChatGPT Work`, `Ads Manager` and **`CLI`**, which is the row a Codex user opens the tree for, and folds the two `Login` components into one. So Claude is read from `summary.json` at one request, and OpenAI costs a second to `proxy/<host>` for the tree. That is the one place this deviates from #84's "one request per provider per poll", and it buys the feature the issue defers to its follow-up. **The wording is the vendor's**: the sentence, the component names, their order and their nesting are all copied rather than composed, `only_show_if_degraded` and `hidden` rows are dropped because the page drops them, and a status token this build does not know prints humanised instead of blank. **The tree opens as a page of the panel**, not in place and no longer in a card. Expanding it underneath the line made it the one block on the page whose height a click changed; a nested `.popover` fixed that and cost the panel half a second of mis-drawn geometry on the next navigation, which is the note above. A page answers both — the provider page is the same height whether the services have been visited or not — and it needs no ceiling of its own, since `PanelMetrics.maxHeight` and the panel's own scroll view are what bound it, which is what replaced every per-section ceiling in the first place. The block still sits at the foot of the provider page, but the reason is now the question rather than the height: what a vendor says about itself is the least-asked reading there, and the alarm loses nothing by it, since a degraded vendor already colours its own name on the Overview. What is deliberately not here: incident history, which is what the link to the page itself is for, and any notification, which belongs to #38's per-alert switch.

## Codex answers for more than one account, and the mechanism is a credential rather than a home.

The limits, the plan and the credits are all on `chatgpt.com/backend-api/wham/usage`, which answers 200 to a bearer token under any User-Agent — measured 2026-09-17, the same block the tail parses off `token_count`, live: the endpoint said 32% where the freshest rollout on that machine was 1 h 51 m old and said 30%. So `CodexUsageSource` is **one reader per credential**, and which account it answers for *is* which credential it holds. The CLI's own `auth.json` is one of them, built with no account of its own because which account that file holds is the CLI's to change; every other is an OpenAI sign-in the user made in `VendorLoginWindow`, filed in a keychain item of Sissy's own (`com.radonforge.sissy.codex-oauth`). **That is deliberately not CodexBar's `CODEX_HOME` per account**, which is the trade #130 rejected and has a defect worth naming: a plain `codex` uses the ambient home, so the extra accounts are the ones the user is not working in. Here nothing is written where a `codex` could read it, so linking an account cannot change which account the terminal is on — and unlinking one cannot either. Four things about it are settled. **The row key is the login, not the workspace**: `chatgpt_user_id`, which is stable across a refresh where the tokens are not, with the workspace recorded beside it in `codex-accounts.json` — a login holding two workspaces is metered twice and membership order is the server's, so the link asks once (`backend-api/accounts`) and records the answer, exactly as the Claude link does for an organisation. A workspace list that could not be read costs the row a name and never the login, because the credential already names the workspace OpenAI defaults it to. **Renewal is ownership**: `CodexCredential.refreshToken` is nil for every credential read from `auth.json`, so "Sissy never renews the CLI's credential" is a property of the value rather than a rule each caller has to remember — the token is one-time, and redeeming the CLI's would strand the terminal. Sissy's own copies it does renew, and files the renewal in the same breath, because OpenAI rotates the refresh token. **The two readings are settled by their stamps, not by rank**: `CodexSignals.merge` takes the later of the tail's and the reader's, which is self-correcting in both directions — a poll is newer than the last turn by construction, and a reader that has stopped hands the row back to the turns without anything having to remember which is preferred. **And the sign-in is the Codex CLI's own client id**, which is public by construction and in every `auth.json` on the machine. That is the one part of this that is a trade rather than a measurement: the alternative was spawning `codex login` against a home of Sissy's own, which needs the binary on `PATH` and shows the same page. What a linked Codex account does **not** get is a spend of its own — a rollout names no account, so the day belongs to the config home exactly as Claude Code's does — and no `Use in CLI`: Sissy signed that account in for itself, it never took the CLI's, and there is nothing to put back.

## Claude's limits come from the CLI's own credential, and Sissy asks for no permission to read it.

`<home>/.credentials.json` holds the OAuth token in plaintext with scopes including `user:profile` — the scope #103 road 2 died for lacking — and measured 2026-09-15 it answers `api.anthropic.com/api/oauth/usage` with HTTP 200, live windows and a `spend` block. Where there is no file the same credential is in the login keychain, read through `/usr/bin/security`: a keychain item's ACL names *applications*, Claude Code files its item by shelling out to that tool, so `security` is on the ACL and Sissy is not. Measured the same day on macOS 27 from a process that had never touched the item, a read and a write both returned 0 with **no dialog**, where an in-process `SecItemCopyMatching` raises the legacy Allow/Deny panel and earns a grant that dies at the next token refresh. That is why there is no longer a "Show Claude Code limits" switch: it existed only to make that prompt expected, and there is no prompt. It also grants Sissy nothing new — any process running as this user can read those items the same way. Sissy never writes the CLI's credential except on an explicit switch, and never refreshes: Anthropic's refresh tokens rotate on use, so spending one would sign the user out of their own terminal. The ceiling is the access token's own life, so a CLI that has not run for hours shows no live limits until it is used again.

## A vendor's refusal outlives the process that met it, and it belongs to a credential rather than to a reader.

A 429 is published as `ProviderLimitsState.rateLimited(until:)`, which lived in memory alone — so every rebuild spent a request on a vendor that had already said no, and that request is not free: measured 2026-09-17 against `api/oauth/usage`, three refusals between 08:26 and 08:30 pushed the deadline from 08:26:44 to 09:30:24, the ceiling. A fresh reader is not a rare thing either: a launch, a provider switched off and on, and every build of a dev loop. `LimitsBackoffStore` is the answer — one store for every reader, in `limits-backoff.json`, deliberately not in `server.json`, whose writes these reader actors would race for the reason the backfill's record documents. It is consulted in front of every request rather than once at launch, because a reader stopped and started inside a block would otherwise spend one, and what it hands each reader is a `LimitsBackoffSlot` for that reader's own key: the vendor refuses a credential, not a Mac. Which is also why `activateClaudeAccount` clears it — the block was earned by the token that has just been replaced, and keeping it left the account switched *to* with no limits until a deadline its own token never met. A reading takes the entry out, a deadline past is not a block, and one further out than `retryAfterCeiling` is clamped, because the file is foreign input like any other.

## A reader the vendor is refusing does not hold the row against a fresher one.

`ClaudeCodeSignals.merge` ranks the CLI's own credential over the claude.ai session — the vendor's own endpoint over the fallback for a Mac that keeps no credential — and both of them run, so rank decides an ordinary day. The one thing that unseats it is a refusal: measured 2026-09-17, the probe was refused from 15:15 and the row stood on its own 15:12 reading with nothing but its age moving, on an account that had a claude.ai reader polling beside it — which could not take the row however much later its reading was. So a blocked reader keeps the row only while its own reading is the later one. It is the rule `CodexSignals.merge` already settles its two sources with, narrowed to the case where rank is what goes wrong. A reader that has read nothing is not in that comparison — it cannot be newer than anything — but its state still reaches the row, because the notice is the only way back from most of them. **And a reader that has withdrawn its reading is out of that comparison, which is what the stamp is for.** `publishFailure` clears `limitsObservedAt` along with the windows: it names the moment *this reading* was taken, and there is no longer one. Keeping it let a reader compete on the freshness of an answer it had already taken down — a probe refused at 15:20 whose last good reading was 15:12 outranked a session that had read at 15:10 and won the row with no windows on it at all. Widening the state test instead was tried and is the wrong fix: it treats the symptom, still loses the row whenever the refused reader's stale stamp happens to be the later one, and leaves the same defect under `signedOut` and `needsAuthorization`. A 429 deliberately does not go through `publishFailure`, because that reading is still the last true one and its age is the point. What this costs is the notice: where another reader is answering, the row shows that reader and says nothing about the refused one — which is the same trade the merge already makes for a reader that has never read at all. **`ClaudeLimitsProbe` answers a 401 or 403 with `.credentialRefused`**, on the grounds the other two readers already answer their own with: a token the endpoint will not accept is precisely the case where the windows on screen are known to be another account's, and they would otherwise have stood for up to a week. It is its own state rather than `sessionExpired` — that one says "link again", and this credential is Claude Code's, rotated by the CLI on its own schedule, so the honest notice carries no action at all. It is also not lifted by the next poll's credential read, because reading a credential says nothing about whether the vendor has started accepting it, which is why `isAnsweredByACredentialRead` excludes it exactly as it excludes a block.

## If Sissy switches accounts, Sissy owns the archive.

The CLI's keychain slots are **scratch**: the unscoped `Claude Code-credentials` and each `Claude Code-credentials-<sha256(NFC(configDir))[:8]>` hold whichever account is active, and the CLI rewrites them with a rotated token on every refresh. Measured 2026-09-15 the hard way — writing account B into the unscoped item let a `claude` on `~/.claude` adopt it, refresh it, and overwrite account A's only copy in its own scoped item *and* `~/.claude/.credentials.json`; refresh tokens rotate, so A was gone from the machine entirely and cost ≈$36 billed to the wrong org before anyone noticed. `ClaudeAccountRegistry` is the answer: it watches the active credential, asks Anthropic whose it is whenever it sees one it has not archived — a switch, a `/login`, or a rotation — and files a copy under that account's uuid in a keychain item of Sissy's own, with an index beside it that holds identities and never a token. An account becomes switchable the first time it is used on this Mac and stays switchable, with no directory, alias or variable to configure. What it cannot do is offer an account that has never signed in here; that first `/login` is the user's. This is a deliberate exception to "nothing Sissy does to the machine outlives Sissy" — it stores credentials and it writes the CLI's slots — and it earns it the only way it can: the switch runs from one click and nothing else, and nothing it holds reaches the frame, the logs, the diagnostics or the export. What it does **not** yet earn is a way out from inside Sissy. There is no control that deletes an archived credential and no code behind one — a `forget` chain was written ahead of its UI and removed unused — so the README names the keychain item and sends the user to Keychain Access. That is a debt against this rule, not a settled shape. **Unlinking is the session's, never the credential's.** The trash on a Settings row takes the claude.ai session and nothing else: that is the half the user added and the half Sissy can put back, one window away. The archived credential is the half Sissy took itself, and there is no second copy to make — `/login` mints one and it is the user's. Deleting it while the CLI is on that account leaves exactly one copy, in a slot the next `Use in CLI` overwrites, and refresh tokens rotate, so the account is off this Mac until a terminal signs it back in. A delete must not reset `lastSeenToken` either, or `captureActive` re-archives the still-active account on its next poll; leaving it alone means the CLI has to rotate first — 26–73 minutes measured — which is how long that single copy stands alone. Whatever eventually deletes an archived credential is therefore its own control with its own words, off `ClaudeAccountStore`'s list rather than `ClaudeWebSessionIndex`'s; the two lists have separate lifetimes for exactly this. **That delete asks before it deletes, and it is a named item in the row's own menu rather than a bare trash.** A session is a secret the user cannot read back and never typed, so the one click that removes it is not a click to get wrong — measured the hard way on the dev build, pressed by accident on the account its owner was signed into, where nothing visibly changed because that account's limits were coming from the CLI's own credential anyway. What made that press available was a row whose *only* visible control was the destructive one, so the trash became `Unlink…` under an `ellipsis` (`CredentialRowMenu`), still `role: .destructive` and still behind the confirmation, beside the copy the row's own text is not selectable for. The menu is what earns the second half: `ForgeSettingsView`'s rows carry `Reconnect…` in it, which is a verb no glyph can spell — the circular arrow already means `Refresh now` on the panel's forge row, and macOS draws no icon inside a SwiftUI menu item. "Cheap to link again" is a reason not to make the delete unrecoverable, never a reason to skip asking.

## The claude.ai session is the fallback for a Mac whose CLI keeps no credential file.

It led this list until the credential file above was measured, and it is kept because that file is Claude Code's and a Mac may not have one. `VendorLoginWindow` signs in at claude.ai once — on the click, never on a poll — and the session is filed in a keychain item Sissy owns (`ClaudeWebSessionStore`); `ClaudeWebSource` then polls `claude.ai/api/organizations/{org}/usage` for the windows *and* the credits, and a linked session's reader runs *beside* the CLI's probe rather than instead of it, and `ClaudeCodeSignals.merge` is what picks between the two readings. **A sign-in rather than a copy of somebody else's**: the import that preceded this read Claude.app's cookie store, which measured well — Claude.app held a `sessionKey` good for four more weeks where Chrome's had expired three and a half months earlier and Safari held none — but it could only ever produce the one account that app was signed into, which is the whole of what #167 needed more than one of. What survives it is the item: a session Sissy owns, not a copy it keeps re-reading, where `Claude Code-credentials` is rewritten every token refresh. That is the whole difference from #103. Three things about the wire are measured and not guessable: the `Claude/<version>` product token in the User-Agent is what gets past the edge (a plain Chrome agent is 403, and `Electron/` does not substitute), the plaintext carries 32 bytes of Chromium domain-binding hash in front of the value, and an account can hold several organizations — the subscription is the one whose `capabilities` name `chat`, never the first one listed. The cookie is a whole claude.ai session, not a read-only usage token: it is never logged, never on the frame, never in the diagnostics or the export, and `ClaudeWebSessionSecrecyTests` is what holds that. **The sessions are the record, the links are a naming, and any list of accounts reads the record.** `UsageEngine.store(session:as:)` files the session and then tries to name it, catching a failed `remember` and keeping the session — losing a login to a disk error is worse than deriving an organisation — so a session with no entry is a state the ordinary path produces, and its reader polls claude.ai either way. `hasClaudeWebSession` and `rebuildClaudeWebSources` already answer off the stored sessions; a Settings list that read the links instead left one of two stored sessions with no row and no way to stop it, measured on the dev build 2026-09-16. `ClaudeWebAccount.list` is the join, driven by the sessions: the link names an account, failing that the account archive, failing that its own uuid — a poor label and the only honest one, and a row under it is what makes that session removable at all. The holding key is not an account and gets no row, for the reason no reader is built for it.

## Codex writes more `token_count` events than there are turns, in two ways, and `last_token_usage` alone cannot tell.

The per-turn block is the right field (see **Codex token convention** in [`AGENTS.md`](../AGENTS.md)) but not the whole question — *whether this event is a turn at all* is answered by what surrounds it. **`total_token_usage` is the authority on the first way**: Codex re-emits the previous turn's block verbatim when a session ends or is interrupted, leaving its own running total untouched, so an event whose total has not moved since the last one carries nothing new. Compare the block field by field rather than the one scalar — two readings whose totals match by coincidence while the breakdown moved are a turn. **A session's own `session_meta` answers the second**: one opened from another — a forked conversation (`forked_from_id`) or a spawned subagent (`source.subagent.thread_spawn.parent_thread_id`) — writes that parent's entire history into its own log at creation, every copied event stamped within a millisecond or two of the session's start where a turn it actually ran takes seconds to come back. `CodexAdapter.replayedTurnWindow` is that separation, and it is a band rather than an edge: measured across a year of rollouts, anything from 50 ms to 3 s reproduces `ccusage` exactly, and 1 s is both the middle of it and ccusage's own constant. The gate on the parent marker is not optional — applied to sessions that copied nothing it takes real turns off the day, measured on two. Both rules are deliberately per-file: ccusage instead reads the *parent's* rollout to recognise the copy, and a tail that opens a second file to understand the one in front of it is a different design. Both pieces of bookkeeping therefore ride on `codexResume.fileModels` (`cumulative`, `copyingThrough`), because the repeat lands after the turn it repeats and a relaunch can fall between them. Measured 2026-09-14 before the fix: **1.8% over a year, 12% of July 2026** — a session forked three times replayed the same history three more times — and 4.5% of that day. With both rules Sissy lands on `ccusage codex` exactly, to the token and the microdollar, across all 55 days it has data for. The `pricing-oracle` fixture carries both shapes for the reason it carries a four-copy Claude turn: a rollout of one `token_count` per turn bills the same either way, which is how this shipped past it. A fork in that fixture has to be causally coherent — one that copies a turn its parent had not taken yet is a log Codex could not have written, and the two tools legitimately disagree on it.

## A provider is named in nine places, and every one of them already has a default.

Adding one is a checklist rather than a refactor: `ProviderID` (`ProviderReadiness.swift`); its data-dir field and `ProviderToggles` with its subscript (`ServerConfig.swift`); `AccountDefaults.home`/`dataDir` and `ServerConfig.providerHome` (`ProviderAccounts.swift`); the construction arm in `UsageEngine.init`; `FrameBuilder.providerSortOrder`; `UsageFormat.providerName`; `ProviderPalette.tint`/`mark` plus the imageset; `ProviderStatusFeed.published`; and the `--scan-provider` arm in `main.swift`. `UsageEngine.persistenceURL` is deliberately not on the list — every provider but Claude Code already takes a file named after its own id. **None of the nine fails on an id it does not know** — the sort falls to `2`, the mark falls to a tinted dot, the tint to `.secondary`, the status feed to no row, the toggle to `nil` — so a provider that has only its adapter and its id renders as a plain row and counts correctly. That is what makes a registry unnecessary at two providers and cheap to justify at four: #35 designed one, and the measurement that deferred it is that the duplication it existed to kill was in the *readers*, which #68 already collapsed into `LocalUsageProvider` + `SourceAdapter`. Build the registry when a third provider has shown what a manifest entry must carry — the candidates surveyed in #35 each break a different assumption a Claude-plus-Codex manifest would bake in (Grok prices from the log line, OpenCode spans vendors and is not a byte-offset tail, Gemini is not append-only), so one designed today would be designed twice.

## A provider switched off is a new engine, not a mutated one.

`UsageEngine`'s lifecycle is terminal — `stop()` cannot be undone — so `UsageEngineHost.setProvider` persists through `UsageEngine.setProvider` and then tears the engine down and builds another from the file. It costs what a relaunch costs, which is nothing: every reader resumes from its own snapshot's offsets, so no tree is re-scanned and no day is counted twice. Three things ride on that rebuild and are not optional. The frame on screen is **cleared**, because it still counts the provider that was just switched off and a panel that goes on showing it reads as a switch that did nothing. The agent hooks are **not** re-affirmed — `start(isLaunch:)` is that distinction — because those are lines in two other programs' configuration files and a switch flipped in Settings has no business rewriting them. And the row is shown thrown **before** the rebuild rather than after, because tearing an engine down flushes every reader's offsets first and the switch would otherwise sit in its old position for the length of that flush. What a switched-off provider keeps is its snapshot and its archive: retention is the engine's and bounds the days of a provider it never built, so switching one back on resumes rather than cold-scans.

## User-facing copy carries no em dash.

Measured 2026-09-21. Commit f1f9e14 (2026-09-16, "docs(readme): rewrite around what the app shows today") took README.md from 9 em dashes to 0. It climbed back to 20 across seven documentation commits: 2 at 18cf7fb, 5 at 152858f, 8 at 506844f (2026-09-17), then 15 at 12b8b6b, 18 at 40f6e71 and 20 at e22e4c3, the last three all on 2026-09-21, days before a release. **The regression was the aside habit, not the long period that produced it**: 15 of the 64 prose sentences README.md carried at e22e4c3, before the cleanup this entry records, had a dash aside, against 0 in f1f9e14, at the same average length (19.4 words against 18.0) — f1f9e14 in fact had more sentences over 35 words, 11 against 6, so a longer file was never the trigger. The dash was the outlier inside the app's own copy too, not just the README's: it joins two clauses with " · " in 56 places, against 12 user-visible strings that carried a dash instead. The reason it came back is that the zero state f1f9e14 reached was never written down anywhere — no rule in AGENTS.md, in docs/, in the deleted CLAUDE.md, nowhere — while AGENTS.md itself carries 82 em dashes and this file 196, so every documentation pass since read a dash-dense house voice and reproduced it in the one file meant to read differently. Those two counts are why the rule stops at the README, SECURITY.md, CONTRIBUTING.md, CREDITS.md, CODE_OF_CONDUCT.md, NOTICE and the app's own Swift strings: AGENTS.md and docs/ are that house voice, not product copy, and a rule that reached them would be asking this file to fail its own check on every future entry. The precedent for mechanizing a zero state rather than trusting a reading to hold is `scripts/check-doc-refs.py`, whose first run found two stale symbols that had survived every human reading of those files; `scripts/check-prose.py` does the same job for the dash, and does not carry a baseline, because after the cleanup that produced this entry the scope it checks is clean and a baseline would be dead configuration.
