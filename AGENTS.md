# AGENTS.md

Guidance for coding agents working in this repository.

## Repository layout

- `app/` — macOS 26+ Xcode workspace, two targets:
  - `Sissy` — menubar SwiftUI app (`app/Sissy/`) with the metering engine (`app/SissyCore/`) compiled in.
  - `sissy-cli` — the same engine behind a command-line entry point, for CI only. Nothing ships it to a user.
  Xcode project generated from `app/project.yml` via XcodeGen — never hand-edit `Sissy.xcodeproj`. Bundle id `com.radonforge.sissy`, team `AS75YRKL95`.
- `docs/ARCHITECTURE.md` is the source of truth for the frame shape + module map; read it before changing `FrameData`.

The ESP32 companion that used to live in `firmware/` is gone from master as of 0.2.0. The last state where it built and paired is the `companion` branch. Archive it on a **branch, never a tag**: `scripts/version.sh` resolves `MARKETING_VERSION` with an unfiltered `git describe --tags`, so any reachable tag becomes the version.

## Common commands

### macOS app + CLI (run from `app/`)

```bash
xcodegen generate                                                      # regenerate Sissy.xcodeproj from project.yml
xcodebuild -project Sissy.xcodeproj -scheme Sissy -configuration Debug build
xcodebuild -project Sissy.xcodeproj -scheme sissy-cli -configuration Debug build
../scripts/dev-build-app.sh                                            # signed local app for login-item testing

# Self-test (pure formatters + pricing tables)
xcodebuild -project Sissy.xcodeproj -scheme sissy-cli -configuration Debug build \
  && "$(xcodebuild -scheme sissy-cli -showBuildSettings | awk -F= '/BUILT_PRODUCTS_DIR/{print $2; exit}' | xargs)/sissy-cli" --self-test

# Scan-once mode (compare against `npx ccusage@latest claude --json` or
# `npx ccusage@latest codex --json` — never a bare `ccusage`, which may be the Homebrew build)
"$(xcodebuild -scheme sissy-cli -showBuildSettings | awk -F= '/BUILT_PRODUCTS_DIR/{print $2; exit}' | xargs)/sissy-cli" --scan
"$(xcodebuild -scheme sissy-cli -showBuildSettings | awk -F= '/BUILT_PRODUCTS_DIR/{print $2; exit}' | xargs)/sissy-cli" --scan --scan-provider codex
```

`sissy-cli --config <path> --backfill` runs the archive backfill against that config's own state dir and dumps the archive as JSON, which is the shape `ccusage <provider> --json` answers in. It is how the backfill's agreement with the oracle is asserted: `--scan` cannot, because it runs the tail's 48 h window and reports today, so every day a backfill writes is invisible to it.

`sissy-cli` is a CI tool, not a product: nothing ships it to a user, and with no flag it prints the list above and exits 2. **Build the scheme before any of the three invocations above** — `-showBuildSettings` resolves `BUILT_PRODUCTS_DIR` without building, so on its own it runs whatever the last *successful* build left there. A `--self-test` that answers `ALL PASS` from a binary the current source no longer compiles into is the failure mode, and a `--scan` compared against `ccusage` on a stale binary is the same trap with numbers instead of a verdict.

The login item and the one-shot retirement of the legacy agent both go through `SMAppService`, which must be tested from a normally signed app bundle. `CODE_SIGNING_ALLOWED=NO` is fine for CI compilation/tests, but launching that product locally makes macOS reject `Contents/Library/LaunchAgents/com.radonforge.sissy.server.plist`.

Adding/removing Swift files requires re-running `xcodegen generate` — the project file is generated, not tracked semantically. The engine sources live in `app/SissyCore/` and compile into both targets; the app target in `app/Sissy/`.

### CI

`.github/workflows/ci.yml` runs shellcheck, actionlint and the docstring-reference check on ubuntu, then `xcodebuild` for both targets, the unit tests and `--self-test` on macos-26. `pricing-oracle.yml` asserts cost agreement with `ccusage` on a synthetic fixture, and `release.yml` builds, notarizes and publishes on a pushed tag.

## Architecture

### Data flow (end-to-end)

```
~/.claude/projects/**/*.jsonl ──► LocalUsageProvider(ClaudeCodeAdapter) ─┐
                                                                          ├─► UsageAggregator ──► UsageEngine ──► FrameData ──► SissyModel
~/.codex/sessions/**/*.jsonl  ──► LocalUsageProvider(CodexAdapter)      ─┘
```

**One tail, one adapter per log format.** `LocalUsageProvider` is the tail both trees are read through: enumeration, per-file offsets and mtimes, the FSEvents watcher, the safety-net poll, the dedup ledger, the day buckets, snapshot load and save, the emit throttle. A `SourceAdapter` owns exactly what differs — which bytes on a line are worth a JSON parse (`lineMayCount`), what a line costs (`event(from:seen:)`), and which of its own state has to survive a relaunch (`resume` / `resumeState`) — plus a `SourceSignals` for what has to be readable from outside the actor. Adding a provider that reads local JSONL is an adapter, not a second tail; the two readers it replaced had drifted to 428 identical lines. A source that is *not* a local log tree is a new `UsageProvider`, which is the protocol the aggregator actually depends on.

`UsageAggregator` sums per-day totals across N `UsageProvider` instances and `UsageEngine` builds a single combined frame from them. One process: the app runs the engine in-process and the frame is a Swift value, not JSON. There is no wire contract to keep in step any more — `FrameData`, `ProviderSlice` and `UsageWindow` live in `app/SissyCore/FrameBuilder.swift` and the app renders those types directly.

**The frame carries numbers, the app words them.** `tokens`/`cost`/`burn` are `Int`, `Decimal` and an optional rate in tokens per hour; `UsageFormat` is the one place any of them is rounded for a surface. They were pre-formatted strings for as long as the frame was rendered into 128×64 pixels, and that shape is what obliged the app to carry a second set of formatters kept in step with the engine's by hand — reintroducing one is reintroducing that. Alongside them the frame carries a raw `providers` array so the header subtitle, the panel's per-provider rows and each provider's rate-limit gauges all come from one payload. A provider that has spent nothing today keeps its slice — it also carries the plan, the account, the credits and the gauges, and dropping it took a whole provider page off the panel until the next turn — while a provider that has produced no reading at all has none, because no reading is not a reading of zero.

**Everything a source answers for besides its totals is one value.** `ProviderSignals` (`UsageAtomics.swift`) holds the windows, the plan, the tier, the account, the credits, why the limits are missing and when each was observed; a source publishes it whole through `SourceSignals.currentSignals()`, which is nonisolated because the aggregator reads it while the emitting provider still holds its actor. One value rather than a getter each is what stops a row pairing one moment's plan with another's windows, and it is also what makes "has anything about this provider changed" a single comparison — which is how an authorization that lapsed reaches the panel on a day where no token event follows it.

`app/SissyCore/` also builds `sissy-cli`, which CI drives for `--self-test`, `--scan`, `--dump-seed` and `--refresh-catalog`. Only `main.swift` and `SelfTest.swift` are the tool's own; every other file in that directory is compiled into the app too.

The mood pop-up, Sissy's state machine and the milestone celebrations are gone as of 0.2.0, and with them `state`, `pickState`, `StateThresholds` and the `MilestoneTracker`. They were the reason the app carried thresholds in dollars, which meant nothing to anyone whose daily spend sat far from them. Don't reintroduce a decorative signal on the cost axis; a signal that earns the top of the panel sits on rate-limit pressure, which reads the same for every user. **What that must not be is one number.** A single headroom gauge led the Overview until 0.2.0 and was removed: one gauge across N providers reports the tightest and silently implies the rest are fine — measured on a day with Claude and Codex both at 100%, it named Codex and Claude vanished. The pressure therefore rides on each provider's own row, where it scales to a third CLI without a redesign, and as of 0.2.0 that row carries the gauge itself rather than a bare percentage: **the Overview's provider block answers whether there is room to keep working and nothing else.** It used to answer the day's split as well — a stacked spend bar with a figure per row — and a rate-limit percentage sitting in a legend for a bar about money named neither the window it measured nor what it had to do with the segment beside it. Pressure is the one reading on the panel that is only actionable *now*; what a period cost is asked at the end of it, and the headline answers that over a window the user picks — `Today · 7 days · 30 days · All`, in a popup on the headline's own row. `All` is everything the archive kept, which `historyRetentionDays` bounds — and it is only honest because #151 indexes what the CLIs already logged: measured 2026-09-15, before it, an archive five days old read $2,100 where those logs held $4,615, and renaming the label was tried and reverted as copy compensating for a defect. That control replaced a fixed 7-day line at the foot of the Overview, and the two were always one question: the line existed only because the headline was hard-wired to today, and it silently included today besides — measured 2026-09-15, 24.7% of it was the headline above it. A calendar month is deliberately not among the windows: it and 30d are the same question with two answers a few percent apart, and it shows two days on the 2nd where a rolling window is always full. The calendar anchor is the invoice question, which needs a last month and a quarter with it and belongs to the report (#81) rather than to a popup in a 340 pt panel. What the control cannot say is that the archive falls short of the window it names, so the grey line under the money says it — `since 11 Sept` — and says nothing when the archive covers it. The plan badge went with the money, for a weaker reason still: it is identity rather than a reading, the same word tomorrow, and it does not even change how the gauge is read. Both are one click away on the page, beside the account they belong to. Every track starts at the same x — a name one glyph wider shortens its own bar, and two bars of different lengths stacked cannot be compared, which is the whole reason they are stacked. **That is a line of its own rather than a column floor, as of 0.2.0.** Floors cannot deliver it in a panel 340 pt wide: measured 2026-09-16 on an account with two organisations, the Claude row's name wants 137.5 pt, its column yielded 85, so the name truncated mid-word *and* took 23 pt off its own track, which started at x=216 against Codex's x=194 and ran 93 pt against its 115 — both halves of the rule broken on one row, with `100%` wrapping to two lines in a 32 pt column that a three-digit reading needs 33.8 pt for. A bar under the row starts at the gutter and runs the full width on every row by construction, the name has the panel rather than a column, and the period and its figure sit at the end of the text line as one run. It costs 8 pt a row.

**Which window a provider leads on is decided by the pace, not by the reading.** `UsagePanelSnapshot.binding` takes the window the current rate empties before its own reset, soonest first; one that survives its reset does not bind however full it is, and the percentage is the fallback for windows that project nothing, where the most spent leads. Ties go to the shorter period. It was the highest percentage until 0.2.0, which put emphasis and caption on two different axes — a session at 40% that lasts until reset outranked a weekly at 35% running out in two days. The pace itself is measured from `limitsObservedAt` rather than the clock: the vendor's percentage is frozen at the reading, so measuring elapsed time against now slid the mark right while the bar stood still, and a Codex reading — which arrives only on the CLI's own turns — grew a point of headroom it never measured every fourteen minutes of a week it had no news of. The row that binds is drawn a step *up*, never the others a step down: dimming them to 55% put their label and caption at 0.30 alpha against the 0.25 macOS draws disabled text at, and every window but one read as a control switched off. **The colour on the row stays on the reading, not on the projection** — colouring a row whose rate empties it before the reset lit both providers on a real day, one at 36% with four hours in hand, because spending above pace at all projects a run-out eventually. What the pace has to say is already there: the bar's mark goes red the moment the fill passes it. **A window whose reset has passed keeps its row and loses its figure.** It used to be dropped before it was ever published, on the grounds that a period past its reset no longer exists — which is true of the *reading* and false of the row. Codex is where that showed: its buckets rode the CLI's own turns alone, so between a reset and the next turn the session row left the page entirely, with the weekly beside it still drawn under a caption implying the block was current — measured 2026-09-16, a 5 h window resetting at 12:30 UTC was gone at 12:55. `CodexUsageSource` has since put a poll behind that row, which shortens the gap to one poll and does not close it: a Mac that is asleep, offline or refused still holds a reading past its reset, and so does every provider between two polls. So `ProviderSignals.live()` only sorts, and `UsagePanelSnapshot` words the roll-over: a dash where the percentage was, no bar at all, and `rolled over 14:30 · awaiting a reading` under it. The dash rather than a bar at zero is the Overview's own rule for a provider that has answered nothing — an empty gauge is a measurement and this is the absence of one — and it is why such a window never binds, so a period that has ended cannot take the emphasis on the page or the Overview's one gauge. Strictly past the reset, never on it: a reading taken at the instant a period ends is a window with nothing left to project from, which the panel already draws as a percentage with no pace under it.

### Engine modules (`app/SissyCore/`)

The per-file map lives in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#engine-modules-appsissycore) — one table, so a module's note cannot drift between two files.

### macOS app

Menubar-only (`LSUIElement: true`). Sandbox disabled, network-client entitlement on for the things that leave the machine, all of them readings the user asked for: the LiteLLM pricing catalog, and — under the limits switch — either Anthropic's usage endpoint or claude.ai's. It asks for no other permission — the USB entitlement and the CoreLocation and local-network usage strings existed only for pairing an ESP32 and went with it. Don't reintroduce a permission prompt without a reason a user would accept at first launch.

`UsageEngineHost` is the app's one hop between the engine actor and `@MainActor`; nothing else talks to the engine. The app has three surfaces and no windows of its own: a left-click usage panel (`Panel/`, an `NSPopover`), a short right-click `NSMenu` (`Menu/StatusItemController.swift`), and the SwiftUI `Settings` scene (`Settings/`, tabs General/Providers/Forge/About) — reachable from the app menu's Settings… item (⌘,) and, in code, only through `SettingsLink`, which takes no action closure and is why the panel's own settings button aims the window at a tab through `SissyModel.settingsTab`.

**There is a fourth surface and it is a window, once, to link an account.** `VendorLoginWindow` opens the vendor's own login in a `WKWebView` — claude.ai's for a Claude account, `auth.openai.com`'s for a Codex one — because a credential cannot be had without it and the alternative is asking a user to paste a cookie out of a browser's inspector. **One window for both, because the difference is one line**: Claude's sign-in ends in a cookie the jar receives, Codex's in a redirect to the CLI's loopback address carrying an authorization code, and `Vendor.session` / `Vendor.code` are the two closures that say which. Everything else — the guardrail, the reachability, the question afterwards — is shared, and a second copy of it would be a second place for that guardrail to drift. What keeps the exception from growing into a browser is that there is nothing to browse with: one window, one starting URL, no address bar, no tabs, no history controls, and a non-persistent cookie jar that dies with it. A link click that leaves the vendor's own hosts goes to the default browser rather than being followed — that is what "confined to the vendor" means here, and it is deliberately not a host allowlist: measured 2026-09-16 and 2026-09-17, claude.ai's login answers 403 to anything that is not a real browser and `auth.openai.com` puts a Cloudflare challenge in front of the form, so which identity providers either offers cannot be read from outside, and a guessed list is a window that dead-ends on the one account the user came to add. Redirects are followed, because a sign-in is a redirect chain the vendor owns. A page's request for a second window, which is how an identity provider's popup sign-in starts, is loaded in the same web view rather than dropped, and one the window cannot follow ends the sign-in with a sentence saying so: there is still one window, and a button that silently does nothing is the dead end the absent allowlist exists to avoid.

**The whole link happens in that window, and the window has to stay reachable.** It does not close on the cookie: what follows can need the user — an account with more than one `chat` organisation must be asked which, and a session claude.ai will not answer for has to say so where the person who just typed a code is looking. Finishing in Settings put the rest of the flow on a surface they had no reason to open. Reachability is not a nicety either: Sissy is `LSUIElement`, so it has no Dock icon and no ⌘-Tab entry, and an email-code login *requires* leaving the window to go and read the code — measured 2026-09-16 on the dev build, the window went behind and there was no gesture in the system that could bring it back, while the only control that could reopen it was disabled for the duration. So it floats, the activation policy goes to `.regular` while it is up, and the control that opens it is never disabled: a second press brings the existing window forward rather than opening a second one. **A control that opens a window must not be disabled while that window is open**, because it is the way back to it.

**A linked account answers for itself, and both answers are recorded rather than derived.** `ClaudeWebAccountLink` asks claude.ai two questions before anything is written — whose session this is, and which of that account's organisations it should be read for — and `ClaudeWebSessionIndex` (`claude-web-sessions.json`) holds the pair beside the session the keychain holds. Neither is derivable when it is needed. The identity, because an account reached through a session alone has no archived CLI credential and therefore no entry in `claude-accounts.json`, so its row would carry the raw Anthropic uuid. The organisation, because an account can hold more than one that names `chat` — a personal plan and a team seat on one address — and membership order is the server's, so a reader deriving it per poll is free to derive it differently on the next one. An account with one is linked outright and the user is asked nothing; an account with several holds its session in the engine, unwritten, until they say which, because a link half-written is worse than a login the user has to make again. A session **adopted** from Claude.app records the identity and no organisation: nobody was asked, and a capability-picked one recorded as a choice would give a guess the standing of an answer. The index is deliberately not `ClaudeAccountStore`'s: that one answers "whose CLI credential has Sissy archived", which is what decides whether `Use in CLI` is offered at all, and an account with a session and no credential belongs in exactly one of the two lists.

**One login item, the app's own** — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#lifecycle-and-login-items) covers the retirement of the second. The rule: its state is not mirrored in `preferences.json`. `SMAppService` is the record, and a user who removes Sissy from System Settings' Login Items would leave a mirrored flag claiming something the system had already undone.

## Conventions specific to this repo

Every rule is here. Where one carries a link, the measurement behind it is in
[`docs/DECISIONS.md`](docs/DECISIONS.md) — read that entry before changing what
it covers, because most of them record something already tried and removed.

- **A permission is asked for when the user switches on the module that needs it, never at launch.** [Why →](docs/DECISIONS.md#a-permission-is-asked-for-when-the-user-switches-on-the-module-that-needs-it-never-at-launch)
- **Nothing Sissy does to the machine outlives Sissy.** [Why →](docs/DECISIONS.md#nothing-sissy-does-to-the-machine-outlives-sissy)
- **The archive is the one thing Sissy keeps, and it keeps it on terms.** [Why →](docs/DECISIONS.md#the-archive-is-the-one-thing-sissy-keeps-and-it-keeps-it-on-terms)
- **The archive is filled in once from what the CLIs already logged, by a second pass with a cutoff of its own.** [Why →](docs/DECISIONS.md#the-archive-is-filled-in-once-from-what-the-clis-already-logged-by-a-second-pass-with-a-cutoff-of-its-own)
- **A project is a repository, not a directory.** [Why →](docs/DECISIONS.md#a-project-is-a-repository-not-a-directory)
- **Two counters ride the tail, and they are two questions rather than one.** A *session* is a CLI somebody started; an *agent* is a sub-agent that session spawned, and their sum says neither. [Why →](docs/DECISIONS.md#two-counters-ride-the-tail-and-they-are-two-questions-rather-than-one)
- **How long a day was worked is a reading of the same turns, and it is minutes rather than a span.** [Why →](docs/DECISIONS.md#how-long-a-day-was-worked-is-a-reading-of-the-same-turns-and-it-is-minutes-rather-than-a-span)
- **At what effort a window was worked is a reading of the same turns, and it is per model one click behind the provider's own page.** [Why →](docs/DECISIONS.md#at-what-effort-a-window-was-worked-is-a-reading-of-the-same-turns-and-it-is-per-model-one-click-behind-the-providers-own-page)
- **What the agents are holding is a reading of the Mac, and it needs no permission.** [Why →](docs/DECISIONS.md#what-the-agents-are-holding-is-a-reading-of-the-mac-and-it-needs-no-permission)
- **Sissy reads a repository's commit identity and never writes one.** [Why →](docs/DECISIONS.md#sissy-reads-a-repositorys-commit-identity-and-never-writes-one)
- **A forge is connected by a token the user hands over, and two forges' figures never add.** `ForgeConnection` is keyed by kind and host, so `github.com`, a GitHub Enterprise and two self-hosted GitLabs are four connections; adding one is the switch and removing it is the off, which is how the module stays inside the rule that something switched off reaches no network. The token is **offered, never taken**: `ForgeTokenImport` reads what `gh` and `glab` hold only on the press of the button that says so, and warns first that such a token usually carries write access to every repository — a mechanism that acquires a credential on its own is the one #167 removed. Who the token belongs to is read from the vendor on every poll and never from a CLI's configuration, measured 2026-09-17 on a `gh` whose config named one account for a token that answered as another. And the counters are two readings rather than one: GitHub answers its own contribution-graph total where GitLab answers an event count, so summing them would invent a third belonging to neither — the rule `ProviderCredits` already holds for money in two currencies. Each counter has a switch, and one switched off is not fetched, because on GitLab it is four requests a poll. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) carries the per-counter measurements.
- **The day's split by model is a row of pills under the strip, and it is two tiers because one line does not fit.** Measured 2026-09-22 at `PanelMetrics.width`, which leaves 312 pt: four pills carrying name, percentage and cost on one line want 434.9 pt and three want 325.1, so the block overflows at the third model — the ordinary case, not an edge. Stacking the figures under the name makes a pill as wide as the wider of its two lines rather than as wide as their sum: four Claude pills come to 249.5 pt, four Codex pills carrying that vendor's longest ids to 291.1, and the whole block renders at **171 pt whatever the model count** against the 24 pt a row the list it replaced cost. It shipped first as `ProjectRowView`'s shape with a model in it and that was the defect: indistinguishable from the `By project` list further down the same page, so the panel said one thing twice in one idiom. **Folded past four, which is what the width holds**: three pills are 210 pt of the 312 a page has, four 277, five 344. Past four both of a pill's lines shrink and the *money* truncates first (`62% · $…`, `9% · $0.…`), which cannot be read at all where a shortened name still can; pinning the figures to their ideal width only moved the damage, overflowing the row and clipping the leading pill's first glyphs. The fold is `modelPillLimit`'s — one pill for the rest, carrying their summed share and cost — and it takes the cheapest, the list being dearest first. **One model is one pill, and the floor of two went with the rows.** A row reading `claude-opus-5  8.1M · $8.17` under a headline reading `8.3M · $8.46` printed the same numbers twice, so a one-model day was better off silent; the pill carries the model's **name**, which nothing else on the page says, so a day spent entirely on one model is precisely the day it is needed. Only the percentage is redundant at 100%, and a percentage is not what the pill is for. **The pill does not fill in proportion to its share** — a capsule at 96% beside one at 4% invites a comparison it cannot honour, since the two are different widths, which is the rule the project tracks already follow. The percentage is written and the background is flat. **The pills answer for the day the pointer is on**, and for today when it is on none: they sit under the strip because they are its caption, which is the rule this block already held for the figures — a hover replaces the caption and never the headline, so a figure a reader came for does not change out from under the pointer on its way to the bars. Each `DayRow` carries its own split rather than fetching one on hover: `UsageHistoryStore.series` already decodes every day file the strip draws and used to discard the `models` array inside it, so the split costs the retain and no second read. A day the archive has no file for still gets a bar and gets **no pills** — an absent reading is not a reading of zero, and holding the previous day's split there would break under the block the strip's own rule. The name is the vendor's id with its date suffix and its **vendor prefix** taken off, the prefix only when the leading token is the provider's own name as `providerName` answers it, so `gpt-5-codex` keeps all of itself on the Codex page while `claude-opus-5` reads `opus-5` on Claude's — a rule derived from the header already on screen, never the display-name table that would be the pricing-table regression with different values.
- **Settings has a height budget, and a row shape that pays for it.** `SettingsRootView.maxContentHeight` is 600 pt, and every control is a `LabeledContent` whose label carries its own description. [Why →](docs/DECISIONS.md#settings-has-a-height-budget-and-a-row-shape-that-pays-for-it)
- **One Sissy, two poses.** `SissyModel.sissyAssetName` is the resting silhouette; `sissySleepingAssetName` is the same silhouette with its eye shut, and it is what the menu bar *and* the panel header rest on while nothing is reaching the app. Both are template images, so surfaces tint them and never ship a second copy. The icon is drawn at full opacity in both states — the shut eye replaced a 40% dim, so don't reintroduce one. Sizing is per-surface: the menu bar draws it at 17 pt because the asset carries 20 pt of ink where an unconfigured SF Symbol measures 15, and at native size it reads a third taller than its neighbours. Copy the image before resizing — `NSImage(named:)` returns the catalogue's shared instance.
- **Sissy's motion is one 24-frame sequence.** [Why →](docs/DECISIONS.md#sissys-motion-is-one-24-frame-sequence)
- **A row answers for itself in a menu, and a block too long for a row answers in a page of the panel.** [Why →](docs/DECISIONS.md#a-row-answers-for-itself-in-a-menu-and-a-block-too-long-for-a-row-answers-in-a-page-of-the-panel)
- **The panel's ceiling is the screen it opens on, and no section pays for it.** [Why →](docs/DECISIONS.md#the-panels-ceiling-is-the-screen-it-opens-on-and-no-section-pays-for-it)
- **A surface that is not on screen costs nothing.** `UsagePanelController` builds the panel's `NSHostingController` when the popover opens and drops it in `popoverDidClose`. A closed popover keeps its window, and a host left attached to it keeps a live SwiftUI view graph inside it: `SissyModel` is `@Observable`, so every frame the engine emits bought a layout and a full rasterization of all 340 pt of the panel into a backing store nobody could see, and `PanelSissy` turned each arrival into 23 of those at 60 fps. Measured on macOS 26 against a Debug build, panel closed and the app otherwise idle: **8.7% of a core before, under 2% after** — the main thread alone went from 15% to 1.1%, and 79% of what it had been doing was inside `CA::Transaction::flush`. The rule generalises past the panel — anything that grows a retained host must stop observing when it is not visible, and `sample <pid>` is how you tell.
- **Sissy binds no port, and reintroducing one is a new design.** The server, the bearer token and the 5155/8787 port existed so an ESP32 on the LAN could pull frames. There is one consumer now and it is in the same process. If a second one ever appears — a widget, a CLI reading live state — that is a new decision with its own design, not a revival of the socket.
- **The git tag is the only version source; never hand-edit a version.** `scripts/version.sh` resolves `MARKETING_VERSION` from the latest tag and `CURRENT_PROJECT_VERSION` from `git rev-list --count HEAD`; `release.sh`, `release.yml` and `dev-build-app.sh` pass both to xcodebuild, which reaches both targets in one build. Cutting a release is `git tag -a vX.Y.Z && git push --tags` — there is no bump commit. That tag's annotation is also the release notes: `release.yml` publishes it with `--notes-file` and refuses a tag messaged with nothing but its own version, before the build runs. `--generate-notes` is what it replaced — it lists every PR since the previous tag, ~140 of them for the release after v0.1.8, and answers what changed in the repository rather than for a user. The pair in `app/project.yml` is a `0.0.0` / `0` dev placeholder, and both `Info.plist` files carry only `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)`. Reintroducing a literal in either plist recreates the bug where 0.1.6 and 0.1.7 both shipped build 6; the pre-notarization `verify bundle version` guard in `release.sh` and `release.yml` exists to catch exactly that. The release workflow needs `fetch-depth: 0` — the default shallow clone makes the commit count 1.
- **There is no hand-maintained rate table, and adding one is a regression.** Rates resolve through three sources: `server.json` `pricingOverride` → the LiteLLM catalog fetched at runtime (`PriceCatalog`, refreshed every 24 h, cached in Application Support) → `PricingSeed.swift`. A provider shipping a new model therefore needs **no Sissy release**. If a model prices at $0, fix the seed or wait for the refresh — do not reintroduce a table.
- **`PricingSeed.swift` is generated, not authored.** Regenerate when cutting a release: `sissy-cli --dump-seed > app/SissyCore/PricingSeed.swift`. It is produced by the same Swift parser that validates the runtime fetch, so there is no second implementation to drift.
- **The rate catalog only grows: a model LiteLLM deletes keeps its last published rate.** Every catalog Sissy adopts or writes, `--dump-seed` included, is the previous one with the fresh fetch laid over it. Where a later `ccusage` drops such a model, Sissy keeps LiteLLM's last rate rather than following it. [Why →](docs/DECISIONS.md#the-rate-catalog-only-grows-a-model-litellm-deletes-keeps-its-last-published-rate)
- **ccusage is the cost oracle — specifically whatever `npx ccusage@latest` resolves to.** It prices from LiteLLM too, so reading LiteLLM directly is what keeps Sissy agreeing with the number users cross-check. Where the two would disagree, match ccusage — subscription users never see a token invoice, so agreeing with the community tool beats agreeing with a hypothetical bill. The `pricing-oracle` workflow asserts exact agreement on a synthetic fixture, and invokes it as `npx ccusage@latest`. Verify pricing questions by **measuring** against ccusage, not by reading pricing pages: two independent readings of the long-context rules (an earlier pass here and a Codex review) both got them wrong, and a three-point measurement settled it in minutes.
- **The divergence is a version, not a package manager.** [Why →](docs/DECISIONS.md#the-divergence-is-a-version-not-a-package-manager)
- **A stale `brew` ccusage will never upgrade off itself.** The project moved from `ryoppippi/ccusage` to `ccusage/ccusage` and renumbered *backwards*: the old formula pinned v20.1.0, the current one v20.0.20. Homebrew sorts 20.1.0 as newer, so `brew outdated` stays silent forever and `brew upgrade` is a no-op — a machine that installed it before the move keeps serving the build with the cache-write bug. Only `brew uninstall ccusage` and a fresh install move it. The fix that removes the whole class of confusion is `npm i -g ccusage`, which puts the oracle itself on `PATH`. Note the 1-hour bug is fixed in the current Rust source (`CACHE_CREATE_1H_INPUT_MULTIPLIER = 2.0` in `ccusage-core/src/cost.rs`), so the divergence is version-specific — but that same file bills long context as whole-request substitution where the JS was measured to bill only the tokens above the threshold, so the two implementations still are not interchangeable.
- **A repeated assistant line is a turn still streaming, not a duplicate to drop.** [Why →](docs/DECISIONS.md#a-repeated-assistant-line-is-a-turn-still-streaming-not-a-duplicate-to-drop)
- **Long-context tiers are deliberately not modelled.** Some models publish an above-200k/272k rate. ccusage bills only the tokens *above* the threshold (measured, not inferred — Anthropic's published table reads as whole-request substitution, so ccusage is arguably wrong). Claude Code compacts before reaching the threshold, so the case is near-unreachable; it was implemented once and removed as unjustified complexity.
- **The plan comes from a different place for each provider, and in neither case the obvious one.** [Why →](docs/DECISIONS.md#the-plan-comes-from-a-different-place-for-each-provider-and-in-neither-case-the-obvious-one)
- **A credits reading is the vendor's own figure in the vendor's own unit, and three absences are not zero.** [Why →](docs/DECISIONS.md#a-credits-reading-is-the-vendors-own-figure-in-the-vendors-own-unit-and-three-absences-are-not-zero)
- **A vendor's status is read from the vendor, dated by Sissy, and never inferred.** [Why →](docs/DECISIONS.md#a-vendors-status-is-read-from-the-vendor-dated-by-sissy-and-never-inferred)
- **Codex answers for more than one account, and the mechanism is a credential rather than a home.** [Why →](docs/DECISIONS.md#codex-answers-for-more-than-one-account-and-the-mechanism-is-a-credential-rather-than-a-home)
- **A config home is a place a CLI writes; an account is a credential.** Sissy reads one config home per vendor — `CLAUDE_CONFIG_DIR` / `CODEX_HOME`, or the default — and reports what that CLI spent. It does **not** attribute spend to an account, and cannot: a Claude Code `*.jsonl` carries `cwd`, `sessionId`, `requestId`, `userType` and no identity at all, so whoever was signed in when a line was written is not in the line. Requiring a home per account to recover that was the wrong trade — it is configuration a user never asked for, and a `claude` started with no variable writes into `~/.claude` whichever account is signed in, so the split does not even hold. What the account *does* decide is the identity on the row and the limits under it, both of which come from the credential. `ProviderHome` is the resolved paths of that one home; the one asymmetry it encodes is that with `CLAUDE_CONFIG_DIR` unset the config home is `~/.claude` but `.claude.json` sits beside it at `$HOME/.claude.json`. Attribution per account stays reconstructible later — `ClaudeAccountRegistry` already knows when the active account changes — without any of this coming back.
- **Claude's limits come from the CLI's own credential, and Sissy asks for no permission to read it.** [Why →](docs/DECISIONS.md#claudes-limits-come-from-the-clis-own-credential-and-sissy-asks-for-no-permission-to-read-it)
- **A vendor's refusal outlives the process that met it, and it belongs to a credential rather than to a reader.** [Why →](docs/DECISIONS.md#a-vendors-refusal-outlives-the-process-that-met-it-and-it-belongs-to-a-credential-rather-than-to-a-reader)
- **A reader the vendor is refusing does not hold the row against a fresher one.** [Why →](docs/DECISIONS.md#a-reader-the-vendor-is-refusing-does-not-hold-the-row-against-a-fresher-one)
- **A live limits reader answers for the credits too, including when it has none.** `cachedUsageUtilization` in `.claude.json` is not invalidated when the CLI signs into a different account — measured 2026-09-15, a config naming an account created the day before still carried the previous account's spend, in the previous account's currency (€359.34 against a live $0). So `ClaudeCodeSignals.merge` takes the running reader's credits wholesale rather than letting the cached copy fill in behind a nil. The cache is the answer when nothing live is running, which is every user who never switched limits on, and never an amendment to one that is.
- **If Sissy switches accounts, Sissy owns the archive.** Unlinking is the *session's*, never the credential's, and it asks before it deletes. [Why →](docs/DECISIONS.md#if-sissy-switches-accounts-sissy-owns-the-archive)
- **The claude.ai session is the fallback for a Mac whose CLI keeps no credential file.** [Why →](docs/DECISIONS.md#the-claudeai-session-is-the-fallback-for-a-mac-whose-cli-keeps-no-credential-file)
- **Codex writes more `token_count` events than there are turns, in two ways, and `last_token_usage` alone cannot tell.** [Why →](docs/DECISIONS.md#codex-writes-more-token_count-events-than-there-are-turns-in-two-ways-and-last_token_usage-alone-cannot-tell)
- **Codex token convention.** `CodexAdapter` uses `last_token_usage` as the per-turn delta (verified against real rollout files — summing `last_token_usage` across events equals the final `total_token_usage` cumulative). `output_tokens` is treated as **gross** (it already includes reasoning); `reasoning_output_tokens` is a sub-breakdown of it that nothing reads — adding it to output would bill the same tokens twice. Verified on real rollouts: `total_tokens == input_tokens + output_tokens` regardless of `reasoning_output_tokens`. Same convention ccusage uses, so the two should agree within rounding.
- **A provider is named in ten places, and every one of them already has a default.** [Why →](docs/DECISIONS.md#a-provider-is-named-in-ten-places-and-every-one-of-them-already-has-a-default)
- **A provider switched off is a new engine, not a mutated one.** [Why →](docs/DECISIONS.md#a-provider-switched-off-is-a-new-engine-not-a-mutated-one)
- **Per-provider persistence.** The Claude Code provider writes `usage-state.json` (legacy path) for upgrade smoothness; the Codex one writes `usage-state-codex.json` via `UsageStatePersistence.forProvider("codex")`, and every further account takes a file named by its own key. A schema change in one provider can quarantine its snapshot without invalidating the other.
- **Adding a snapshot field: reach for an optional, not a `schemaVersion` bump.** `UsageStateSnapshot` is shared, so bumping the version discards *both* snapshots — measured 2026-09-10, that costs Claude Code a ~16 s cold scan of `~/.claude/projects` for a change that may tell it nothing. An optional field lets only the adapter that needs it treat `nil` as "cold-scan my own tree" (~2 s for Codex); `codexResume` is the worked example. Bump the version only when the change alters how a token count or cost is *derived*, which is what the field is documented for.
- **Codex resume state is not an optimisation.** `codexResume.fileModels` exists because rebuilding the per-file model map means re-reading every byte already consumed, and the reader emits nothing until it finishes — measured at 110 s on a 43 MB tree, during which the panel has no Codex row at all. `codexResume.rateLimitWindows` exists because the tail's own reading of the limits arrives only on the CLI's `token_count` events: with offsets at EOF there is nothing to re-read, so without persistence the tail has nothing to say until the next turn. It is still what answers on a Mac that is offline, on a token that has expired, and in the moment after a relaunch — which is why it is persisted and why **`CodexUsageSource` did not replace it**. What that reader retired is the *ceiling*: "always one Codex turn behind" was true for as long as the turns were the only source, and it was never a property of the vendor.
- **A docstring's measurement carries its date, and the symbols it names are checked.** A dated claim cannot become false, only irrelevant — `measured 2026-09-16` is what licenses a docstring to carry `137.5 pt` at all, where the same figure undated is read as present tense and eventually lies. A symbol name is the other half and the more fragile one: a number is self-contained and a wrong one is visible, while a name is a coupling to another part of the tree that breaks silently when that end is renamed. `scripts/check-doc-refs.py` takes every backticked identifier out of the `///` lines and fails on one the source no longer declares; platform APIs, environment variables and vendor names live in `.docref-baseline`, regenerated with `--write-baseline` the way swiftlint's is. Measured 2026-09-17 across 153 files: 551 distinct symbols cited in 987 mentions, and **two** stale — `limitsEnabled`, for the Settings switch that went with the keychain prompt, and `selected`, a `make` parameter dropped in 6f22fe2. Both had survived every reading of those files; neither survived the check.
- **Sissy links nothing third-party, and `CREDITS.md` is not a licence file.** The last dependency was SwiftNIO, which the WebSocket server needed; with the server gone the app ships only its own code, so nothing has to travel with the binary and nothing is bundled for it — `AboutTests` fails if a licence file reappears as a resource. `CREDITS.md` at the root credits the projects Sissy *reads* (`ccusage`, LiteLLM), which is courtesy rather than obligation, and About's Acknowledgements sheet lists the same two inline. Adding a dependency means putting the notices back, in both places.
- **User-facing copy carries no em dash.** The rule covers the root docs a user reads — README.md, SECURITY.md, CONTRIBUTING.md, CREDITS.md, CODE_OF_CONDUCT.md, NOTICE — and every Swift string literal under `app/Sissy`, `app/SissyCore` and `app/SissyTests`; AGENTS.md and docs/ are design notes rather than product copy and keep theirs. The app's own separator idiom is the middle dot, as in `Keep awake · holding 12m`, and the one exception is the bare `"—"` literal a window with no reading yet renders as — a documented placeholder, not punctuation. `scripts/check-prose.py` enforces it. [Why →](docs/DECISIONS.md#user-facing-copy-carries-no-em-dash)

## Local fast feedback (pre-commit)

`pip install pre-commit && pre-commit install` once per clone. Subsequent `git commit` automatically runs `swift-format`, `swiftlint`, `check-doc-refs.py`, `check-prose.py`, `shellcheck` and `actionlint` against changed files. Same tools as CI, no version drift.

`pre-commit run --all-files` runs the full sweep.

CI lints against a recorded backlog in `.swiftlint-baseline`, so only **new** violations annotate a PR. Regenerate it from the repo root when the backlog legitimately changes (e.g. after a refactor that adds or clears violations): `swiftlint lint --write-baseline .swiftlint-baseline`.

## Quality gates

Consumed by the `/commit` skill. Run before each commit; `--no-checks` to skip.

```yaml
quality-gates:
  format: xcrun swift-format lint --recursive --strict app/Sissy app/SissyCore app/SissyTests
  lint: swiftlint lint --quiet --lenient && shellcheck scripts/*.sh app/Sissy/Resources/*.sh
  docs: python3 scripts/check-doc-refs.py
  prose: python3 scripts/check-prose.py
```

`test:` is intentionally omitted — `xcodebuild test` is too slow per-commit; CI catches it.
