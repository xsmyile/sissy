# AGENTS.md

Guidance for coding agents working in this repository.

## Repository layout

- `app/` — macOS 26+ Xcode workspace, two targets:
  - `Sissy` — menubar SwiftUI app (`app/Sissy/`) with the metering engine (`app/SissyCore/`) compiled in.
  - `sissy-cli` — the same engine behind a command-line entry point, for CI only. Nothing ships it to a user.
  Xcode project generated from `app/project.yml` via XcodeGen — never hand-edit `Sissy.xcodeproj`. Bundle id `com.radonforge.sissy`, team `AS75YRKL95`.
- `docs/ARCHITECTURE.md` is the source of truth for the frame shape + module map; read it before changing `FrameData`.

The ESP32 companion that used to live in `firmware/` is gone from master as of 0.1.9. The last state where it built and paired is the `companion` branch. Archive it on a **branch, never a tag**: `scripts/version.sh` resolves `MARKETING_VERSION` with an unfiltered `git describe --tags`, so any reachable tag becomes the version.

## Common commands

### macOS app + CLI (run from `app/`)

```bash
xcodegen generate                                                      # regenerate Sissy.xcodeproj from project.yml
xcodebuild -project Sissy.xcodeproj -scheme Sissy -configuration Debug build
xcodebuild -project Sissy.xcodeproj -scheme sissy-cli -configuration Debug build
../scripts/dev-build-app.sh                                            # signed local app for login-item testing

# Self-test (pure formatters + pricing tables)
xcodebuild -project Sissy.xcodeproj -scheme sissy-cli -configuration Debug build \
  && "$(xcodebuild -scheme sissy-cli -showBuildSettings | awk -F= '/BUILT_PRODUCTS_DIR/{print $2; exit}' | xargs)/sissy-cli" --self-test

# Scan-once mode (compare against `npx ccusage@latest claude --json` or
# `npx ccusage@latest codex --json` — never a bare `ccusage`, which may be the Homebrew build)
"$(xcodebuild -scheme sissy-cli -showBuildSettings | awk -F= '/BUILT_PRODUCTS_DIR/{print $2; exit}' | xargs)/sissy-cli" --scan
"$(xcodebuild -scheme sissy-cli -showBuildSettings | awk -F= '/BUILT_PRODUCTS_DIR/{print $2; exit}' | xargs)/sissy-cli" --scan --scan-provider codex
```

`sissy-cli --config <path> --backfill` runs the archive backfill against that config's own state dir and dumps the archive as JSON, which is the shape `ccusage <provider> --json` answers in. It is how the backfill's agreement with the oracle is asserted: `--scan` cannot, because it runs the tail's 48 h window and reports today, so every day a backfill writes is invisible to it.

`sissy-cli` is a CI tool, not a product: nothing ships it to a user, and with no flag it prints the list above and exits 2. **Build the scheme before any of the three invocations above** — `-showBuildSettings` resolves `BUILT_PRODUCTS_DIR` without building, so on its own it runs whatever the last *successful* build left there. A `--self-test` that answers `ALL PASS` from a binary the current source no longer compiles into is the failure mode, and a `--scan` compared against `ccusage` on a stale binary is the same trap with numbers instead of a verdict.

The login item and the one-shot retirement of the legacy agent both go through `SMAppService`, which must be tested from a normally signed app bundle. `CODE_SIGNING_ALLOWED=NO` is fine for CI compilation/tests, but launching that product locally makes macOS reject `Contents/Library/LaunchAgents/com.radonforge.sissy.server.plist`.

Adding/removing Swift files requires re-running `xcodegen generate` — the project file is generated, not tracked semantically. The engine sources live in `app/SissyCore/` and compile into both targets; the app target in `app/Sissy/`.

### CI

`.github/workflows/ci.yml` runs shellcheck, actionlint and the docstring-reference check on ubuntu, then `xcodebuild` for both targets, the unit tests and `--self-test` on macos-26. `pricing-oracle.yml` asserts cost agreement with `ccusage` on a synthetic fixture, and `release.yml` builds, notarizes and publishes on a pushed tag.

## Architecture

### Data flow (end-to-end)

```
~/.claude/projects/**/*.jsonl ──► LocalUsageProvider(ClaudeCodeAdapter) ─┐
                                                                          ├─► UsageAggregator ──► UsageEngine ──► FrameData ──► SissyModel
~/.codex/sessions/**/*.jsonl  ──► LocalUsageProvider(CodexAdapter)      ─┘
```

**One tail, one adapter per log format.** `LocalUsageProvider` is the tail both trees are read through: enumeration, per-file offsets and mtimes, the FSEvents watcher, the safety-net poll, the dedup ledger, the day buckets, snapshot load and save, the emit throttle. A `SourceAdapter` owns exactly what differs — which bytes on a line are worth a JSON parse (`lineMayCount`), what a line costs (`event(from:seen:)`), and which of its own state has to survive a relaunch (`resume` / `resumeState`) — plus a `SourceSignals` for what has to be readable from outside the actor. Adding a provider that reads local JSONL is an adapter, not a second tail; the two readers it replaced had drifted to 428 identical lines. A source that is *not* a local log tree is a new `UsageProvider`, which is the protocol the aggregator actually depends on.

`UsageAggregator` sums per-day totals across N `UsageProvider` instances and `UsageEngine` builds a single combined frame from them. One process: the app runs the engine in-process and the frame is a Swift value, not JSON. There is no wire contract to keep in step any more — `FrameData`, `ProviderSlice` and `UsageWindow` live in `app/SissyCore/FrameBuilder.swift` and the app renders those types directly.

**The frame carries numbers, the app words them.** `tokens`/`cost`/`burn` are `Int`, `Decimal` and an optional rate in tokens per hour; `UsageFormat` is the one place any of them is rounded for a surface. They were pre-formatted strings for as long as the frame was rendered into 128×64 pixels, and that shape is what obliged the app to carry a second set of formatters kept in step with the engine's by hand — reintroducing one is reintroducing that. Alongside them the frame carries a raw `providers` array so the header subtitle, the panel's per-provider rows and each provider's rate-limit gauges all come from one payload. A provider that has spent nothing today keeps its slice — it also carries the plan, the account, the credits and the gauges, and dropping it took a whole provider page off the panel until the next turn — while a provider that has produced no reading at all has none, because no reading is not a reading of zero.

**Everything a source answers for besides its totals is one value.** `ProviderSignals` (`UsageAtomics.swift`) holds the windows, the plan, the tier, the account, the credits, why the limits are missing and when each was observed; a source publishes it whole through `SourceSignals.currentSignals()`, which is nonisolated because the aggregator reads it while the emitting provider still holds its actor. One value rather than a getter each is what stops a row pairing one moment's plan with another's windows, and it is also what makes "has anything about this provider changed" a single comparison — which is how an authorization that lapsed reaches the panel on a day where no token event follows it.

`app/SissyCore/` also builds `sissy-cli`, which CI drives for `--self-test`, `--scan`, `--dump-seed` and `--refresh-catalog`. Only `main.swift` and `SelfTest.swift` are the tool's own; every other file in that directory is compiled into the app too.

The mood pop-up, Sissy's state machine and the milestone celebrations are gone as of 0.1.9, and with them `state`, `pickState`, `StateThresholds` and the `MilestoneTracker`. They were the reason the app carried thresholds in dollars, which meant nothing to anyone whose daily spend sat far from them. Don't reintroduce a decorative signal on the cost axis; a signal that earns the top of the panel sits on rate-limit pressure, which reads the same for every user. **What that must not be is one number.** A single headroom gauge led the Overview until 0.1.9 and was removed: one gauge across N providers reports the tightest and silently implies the rest are fine — measured on a day with Claude and Codex both at 100%, it named Codex and Claude vanished. The pressure therefore rides on each provider's own row, where it scales to a third CLI without a redesign, and as of 0.1.10 that row carries the gauge itself rather than a bare percentage: **the Overview's provider block answers whether there is room to keep working and nothing else.** It used to answer the day's split as well — a stacked spend bar with a figure per row — and a rate-limit percentage sitting in a legend for a bar about money named neither the window it measured nor what it had to do with the segment beside it. Pressure is the one reading on the panel that is only actionable *now*; what a period cost is asked at the end of it, and the headline answers that over a window the user picks — `Today · 7 days · 30 days · All`, in a popup on the headline's own row. `All` is everything the archive kept, which `historyRetentionDays` bounds — and it is only honest because #151 indexes what the CLIs already logged: measured 2026-09-15, before it, an archive five days old read $2,100 where those logs held $4,615, and renaming the label was tried and reverted as copy compensating for a defect. That control replaced a fixed 7-day line at the foot of the Overview, and the two were always one question: the line existed only because the headline was hard-wired to today, and it silently included today besides — measured 2026-09-15, 24.7% of it was the headline above it. A calendar month is deliberately not among the windows: it and 30d are the same question with two answers a few percent apart, and it shows two days on the 2nd where a rolling window is always full. The calendar anchor is the invoice question, which needs a last month and a quarter with it and belongs to the report (#81) rather than to a popup in a 340 pt panel. What the control cannot say is that the archive falls short of the window it names, so the grey line under the money says it — `since 11 Sept` — and says nothing when the archive covers it. The plan badge went with the money, for a weaker reason still: it is identity rather than a reading, the same word tomorrow, and it does not even change how the gauge is read. Both are one click away on the page, beside the account they belong to. Every track starts at the same x — a name one glyph wider shortens its own bar, and two bars of different lengths stacked cannot be compared, which is the whole reason they are stacked. **That is a line of its own rather than a column floor, as of 0.1.10.** Floors cannot deliver it in a panel 340 pt wide: measured 2026-09-16 on an account with two organisations, the Claude row's name wants 137.5 pt, its column yielded 85, so the name truncated mid-word *and* took 23 pt off its own track, which started at x=216 against Codex's x=194 and ran 93 pt against its 115 — both halves of the rule broken on one row, with `100%` wrapping to two lines in a 32 pt column that a three-digit reading needs 33.8 pt for. A bar under the row starts at the gutter and runs the full width on every row by construction, the name has the panel rather than a column, and the period and its figure sit at the end of the text line as one run. It costs 8 pt a row.

**Which window a provider leads on is decided by the pace, not by the reading.** `UsagePanelSnapshot.binding` takes the window the current rate empties before its own reset, soonest first; one that survives its reset does not bind however full it is, and the percentage is the fallback for windows that project nothing, where the most spent leads. Ties go to the shorter period. It was the highest percentage until 0.1.10, which put emphasis and caption on two different axes — a session at 40% that lasts until reset outranked a weekly at 35% running out in two days. The pace itself is measured from `limitsObservedAt` rather than the clock: the vendor's percentage is frozen at the reading, so measuring elapsed time against now slid the mark right while the bar stood still, and a Codex reading — which arrives only on the CLI's own turns — grew a point of headroom it never measured every fourteen minutes of a week it had no news of. The row that binds is drawn a step *up*, never the others a step down: dimming them to 55% put their label and caption at 0.30 alpha against the 0.25 macOS draws disabled text at, and every window but one read as a control switched off. **The colour on the row stays on the reading, not on the projection** — colouring a row whose rate empties it before the reset lit both providers on a real day, one at 36% with four hours in hand, because spending above pace at all projects a run-out eventually. What the pace has to say is already there: the bar's mark goes red the moment the fill passes it. **A window whose reset has passed keeps its row and loses its figure.** It used to be dropped before it was ever published, on the grounds that a period past its reset no longer exists — which is true of the *reading* and false of the row. Codex is where that showed: its buckets rode the CLI's own turns alone, so between a reset and the next turn the session row left the page entirely, with the weekly beside it still drawn under a caption implying the block was current — measured 2026-09-16, a 5 h window resetting at 12:30 UTC was gone at 12:55. `CodexUsageSource` has since put a poll behind that row, which shortens the gap to one poll and does not close it: a Mac that is asleep, offline or refused still holds a reading past its reset, and so does every provider between two polls. So `ProviderSignals.live()` only sorts, and `UsagePanelSnapshot` words the roll-over: a dash where the percentage was, no bar at all, and `rolled over 14:30 · awaiting a reading` under it. The dash rather than a bar at zero is the Overview's own rule for a provider that has answered nothing — an empty gauge is a measurement and this is the absence of one — and it is why such a window never binds, so a period that has ended cannot take the emphasis on the page or the Overview's one gauge. Strictly past the reset, never on it: a reading taken at the instant a period ends is a window with nothing left to project from, which the panel already draws as a percentage with no pace under it.

### Engine modules (`app/SissyCore/`)

The per-file map lives in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#engine-modules-appsissycore) — one table, so a module's note cannot drift between two files.

### macOS app

Menubar-only (`LSUIElement: true`). Sandbox disabled, network-client entitlement on for the things that leave the machine, all of them readings the user asked for: the LiteLLM pricing catalog, and — under the limits switch — either Anthropic's usage endpoint or claude.ai's. It asks for no other permission — the USB entitlement and the CoreLocation and local-network usage strings existed only for pairing an ESP32 and went with it. Don't reintroduce a permission prompt without a reason a user would accept at first launch.

`UsageEngineHost` is the app's one hop between the engine actor and `@MainActor`; nothing else talks to the engine. The app has three surfaces and no windows of its own: a left-click usage panel (`Panel/`, an `NSPopover`), a short right-click `NSMenu` (`Menu/StatusItemController.swift`), and the SwiftUI `Settings` scene (`Settings/`, tabs General/Providers/About) — reachable from the app menu's Settings… item (⌘,) and, in code, only through `SettingsLink`, which takes no action closure and is why the panel's own settings button aims the window at a tab through `SissyModel.settingsTab`.

**There is a fourth surface and it is a window, once, to link an account.** `VendorLoginWindow` opens the vendor's own login in a `WKWebView` — claude.ai's for a Claude account, `auth.openai.com`'s for a Codex one — because a credential cannot be had without it and the alternative is asking a user to paste a cookie out of a browser's inspector. **One window for both, because the difference is one line**: Claude's sign-in ends in a cookie the jar receives, Codex's in a redirect to the CLI's loopback address carrying an authorization code, and `Vendor.session` / `Vendor.code` are the two closures that say which. Everything else — the guardrail, the reachability, the question afterwards — is shared, and a second copy of it would be a second place for that guardrail to drift. What keeps the exception from growing into a browser is that there is nothing to browse with: one window, one starting URL, no address bar, no tabs, no history controls, and a non-persistent cookie jar that dies with it. A link click that leaves the vendor's own hosts goes to the default browser rather than being followed — that is what "confined to the vendor" means here, and it is deliberately not a host allowlist: measured 2026-09-16 and 2026-09-17, claude.ai's login answers 403 to anything that is not a real browser and `auth.openai.com` puts a Cloudflare challenge in front of the form, so which identity providers either offers cannot be read from outside, and a guessed list is a window that dead-ends on the one account the user came to add. Redirects are followed, because a sign-in is a redirect chain the vendor owns.

**The whole link happens in that window, and the window has to stay reachable.** It does not close on the cookie: what follows can need the user — an account with more than one `chat` organisation must be asked which, and a session claude.ai will not answer for has to say so where the person who just typed a code is looking. Finishing in Settings put the rest of the flow on a surface they had no reason to open. Reachability is not a nicety either: Sissy is `LSUIElement`, so it has no Dock icon and no ⌘-Tab entry, and an email-code login *requires* leaving the window to go and read the code — measured 2026-09-16 on the dev build, the window went behind and there was no gesture in the system that could bring it back, while the only control that could reopen it was disabled for the duration. So it floats, the activation policy goes to `.regular` while it is up, and the control that opens it is never disabled: a second press brings the existing window forward rather than opening a second one. **A control that opens a window must not be disabled while that window is open**, because it is the way back to it.

**A linked account answers for itself, and both answers are recorded rather than derived.** `ClaudeWebAccountLink` asks claude.ai two questions before anything is written — whose session this is, and which of that account's organisations it should be read for — and `ClaudeWebSessionIndex` (`claude-web-sessions.json`) holds the pair beside the session the keychain holds. Neither is derivable when it is needed. The identity, because an account reached through a session alone has no archived CLI credential and therefore no entry in `claude-accounts.json`, so its row would carry the raw Anthropic uuid. The organisation, because an account can hold more than one that names `chat` — a personal plan and a team seat on one address — and membership order is the server's, so a reader deriving it per poll is free to derive it differently on the next one. An account with one is linked outright and the user is asked nothing; an account with several holds its session in the engine, unwritten, until they say which, because a link half-written is worse than a login the user has to make again. A session **adopted** from Claude.app records the identity and no organisation: nobody was asked, and a capability-picked one recorded as a choice would give a guess the standing of an answer. The index is deliberately not `ClaudeAccountStore`'s: that one answers "whose CLI credential has Sissy archived", which is what decides whether `Use in CLI` is offered at all, and an account with a session and no credential belongs in exactly one of the two lists.

**One login item, the app's own** — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#lifecycle-and-login-items) covers the retirement of the second. The rule: its state is not mirrored in `preferences.json`. `SMAppService` is the record, and a user who removes Sissy from System Settings' Login Items would leave a mirrored flag claiming something the system had already undone.

## Conventions specific to this repo

- **A permission is asked for when the user switches on the module that needs it, never at launch.** Sissy's first run asks for nothing, and the README says so out loud; that is the reason someone installs a menu bar app that reads their session logs. A module that is off must not exist as far as the system is concerned — no TCC prompt, no notification authorization, no power assertion, no entitlement that only it needs. The Claude Code limits toggle is the worked example, and the claude.ai login beside it is the second: `VendorLoginWindow` opens only from the button, never from a poll or a launch, which is what keeps the one window a user ever sees tied to the gesture that asked for it. It replaced an import that read Claude.app's Safe Storage key — one dialog, on the click — and #167 took that out rather than keeping both: two ways to acquire a session is the third mechanism the issue exists to prevent, and the one that could not name the account it had imported. On the first: the keychain prompt happens when the switch is flipped, not at boot — and that is enforced, not merely intended. `ClaudeCredentialsStore.load(allowingInteraction:)` takes the caller's word for whether it is a user action, and every scheduled read passes `false`, which macOS cannot prompt for. That takes **three** suppressors, not two: an `LAContext` with `interactionNotAllowed` and the runtime-resolved `kSecUseAuthenticationUIFail` travel on the query, and neither touches the legacy keychain's own Allow/Deny panel — measured on macOS 27, a read carrying both still raised it at launch. `SecKeychainSetUserInteractionAllowed(false)` is what closes that door; it is process-wide and deprecated with no replacement, so `load` resolves it by name, throws it around the call alone and restores it in a `defer`. A read suppressed that way answers `errSecAuthFailed` — the *same* status a user clicking Deny produces — so the status alone cannot say which happened and `ClaudeCredentialsStore.classify` takes `allowingInteraction` to decide. Such a read answers `.interactionRequired`, which must never be folded into `.denied`: nobody was asked, so the probe stays alive and the limits stay hidden until the grant returns or the user flips the switch. The grant lapses on every re-signed build, and long before that anyway: Claude Code rewrites the keychain item on every token refresh and the ACL goes with it — measured 2026-09-13, three rewrites of an item created in April, 73 and 26 minutes apart, with no Sissy build in between. So the ceiling on an Allow is a token cycle, not a build, and `.interactionRequired` is the ordinary case rather than the edge one. `ProviderLimitsState` and the panel's notice row make that loss visible and recoverable in a click; they do not raise the ceiling, which needs a different source for the token (#103).
- **Nothing Sissy does to the machine outlives Sissy.** Sissy counts while it is running and stops when it quits; the numbers live in files that are there either way, so a relaunch resumes from persisted offsets and loses nothing. `KeepAwake` is the worked example: the mode persists in `server.json`, the power assertions do not. A hold nobody can see, on a Mac whose menu bar has no Sissy in it, is a battery complaint with no path back to its cause. "Start at login" is therefore the switch that keeps a day complete, and the reason `LegacyAgentRetirement` claims the app's login item on behalf of a user whose counting used to come from the agent, rather than just unregistering it. The mode is `off`, `auto` — held while Sissy can see agents working, which is the one thing a generic `caffeinate` cannot do — or `on`, and only `on` carries a ceiling: `auto` is already bounded by its idle window, and cutting a hold out from under agents that are demonstrably still working is the failure the mode exists to prevent. A manual hold that reaches its ceiling switches itself off rather than going quiet, because "on and holding nothing" already means power management refused the assertion. The hold covers the screen as well as the system by default — a lit screen is a Mac that never locks itself, which is why it hangs off an explicit click and not a default, and why `keepScreenAwake` exists to drop that half for a Mac left running agents unattended. The system assertion is the hold and the screen one is an addition to it, never a substitute: taken alone, a screen blanked by hand would let the Mac idle to sleep under a switch the user left on. What it deliberately cannot do is keep a closed lid working: that needs `pmset disablesleep`, which is root-only and a system-wide setting that survives a crash, a `kill -9` and a reboot — the exact thing this rule forbids. Clamshell on power with an external display is macOS's own feature and needs nothing from Sissy. **The session hook is the one declared exception, and it is not the archive's.** The archive's exception is Sissy's own data in Sissy's own directory, removable by a button in Settings; this one writes a line into `~/.claude/settings.json` and `~/.codex/hooks.json`, which belong to other programs. It earns the exception the only way it can: it is off by default, the ⓘ beside the switch says exactly what will be written before it is flipped, Settings' Files row names both files, and switching it off takes both lines, the script and the inbox back out. What it cannot promise is *when* the lines come out, only that they do: a configuration Sissy could not rewrite leaves `agentHooksRemovalPending` set in `server.json` — written before either file is touched, so a crash mid-removal counts — and the next launch goes back for it, under a switch that is already off. Settings says so and offers the retry. What it cannot promise at all is the uninstall order. A user who drags Sissy to the Trash without switching it off first leaves two lines that fork `/bin/sh`, find nothing at the path they name, drain stdin and exit 0 — inert, but present, in a file they did not write. That is stated in the switch's own copy rather than only here, because it is the part no code of Sissy's can undo. Nothing else may follow it out of this rule without the same four answers and the same admission.
- **The archive is the one thing Sissy keeps, and it keeps it on terms.** `UsageHistory` writes a day-by-model record under `history/` because the day buckets retain two days and the CLIs' own logs are not a record anyone can count on — that is what the panel's week, the export and every per-period question are read from. It is the exception to the rule above, so it carries the conditions that rule exists to protect: its location is named in Settings' Files row, a button deletes it outright, `historyRetentionDays` bounds it, and `0` switches it off. A day is written whole, never appended to, so a cold scan that re-derives it replaces rather than doubles it — but only by a reading **at least as complete** as the one on disk, which is two tests and a reading has to pass both: every **model** at the model's own total, and every row that **names a project** at its own key. Neither alone is enough — the model total alone lets a scan that lost one project's session log pass by outspending it on another, and the row key alone freezes a day whose no-project rows a re-scan has since resolved, since attributing usage is knowing more about it rather than losing it. A day file this build cannot decode is left alone on the same grounds. A day the tail cannot vouch for is left unwritten rather than written short, which is what a relaunch whose offsets are past events the archive never saw produces. **The archive is a projection of the snapshot, never its own resume source**: `UsageStateSnapshot.historyResume` carries the per-model split beside the day totals the snapshot already held, so a resumed day continues at the byte the offsets name and the day file is rewritten whole from there. That is what makes the two writes independent — either can be throttled out or fail on its own, in either order, and the next flush reconciles the file rather than continuing it. Retention is the **engine's**, not the tail's: a provider switched off is never built, and the days it recorded are still bound by what the setting promises. Nothing else Sissy does may follow the archive out of this rule without the same four answers.
- **The archive is filled in once from what the CLIs already logged, by a second pass with a cutoff of its own.** Sissy's archive starts the day it first runs and the CLIs' logs go back months, so a new install is at day zero forever — measured 2026-09-15, the widest window read $2,103 against $4,615 of logs, 53% of it older than the archive. `ArchiveBackfill` is the answer, and it is a second *mechanism* rather than a wider `retainDays`: raising that would grow the live ledger, the day buckets and the snapshot permanently, on every relaunch, to buy a one-time catch-up, and `snapshot.retainDays` would discard both providers' offsets on the way. It is **the same tail and the same adapters** — a `LocalUsageProvider` built with a `backfill` range instead of a rolling window — because the rules that make a metered day land on `ccusage` exactly are the tail's, and a second scanner would be the two readers #68 collapsed, again. The window **ends where the tail's begins**, so the two never write the same day and no coverage check has to arbitrate between them; the day it ends on is the one the tail's rolling window cuts in half and therefore suppresses, which is the only way that day is ever written at all. It **begins at the retention cutoff**, in calendar days rather than as a rolling multiple of 24 hours: a rolling bound sits a day further back, writes a day the next prune deletes, and cuts its own oldest day in half for the reason the tail's does. A day is flushed only once it is **proved** complete — files come newest first, so after one of mtime `M` no unread file can carry a later event and every day after `M`'s is final — which is what fills the panel's windows in while the pass runs *and* what stops an interruption from freezing a day it had read half of, since `isCoveredBy` would refuse to repair that one on a machine where a worktree has since been deleted. A day holding a model no rate covers is **left out rather than written short**, which only a backfill may do: the tail meters a day that is still running, and `applyPriceCatalog` prices from the refresh onwards without repricing what it already counted, so the same refusal there would keep today out of the archive for the whole of it. Nothing is persisted but day files — no snapshot, so the tail resumes from the byte it left off at whether a pass ran or not — and the record of what has been covered is `history-backfill.json`, deliberately **neither** inside `history/`, where deleting the archive would have the next launch re-deriving what the user just asked Sissy to forget, **nor** in `server.json`, whose writes a detached task would race. **The record narrows the next window rather than suppressing it**, and it carries both ends: a record of where a pass *started* cannot tell a day that has merely rolled over from a Mac that was off for a fortnight, which left the feature working exactly once — the tail's 48 h could not reach those days, the record said the window was covered, and nothing ever went back. What the archive is complete through is the later of what a pass covered and how far the tail was running, and the tail's reach is the snapshot file's own mtime rather than the `savedAt` inside it, which is a stat against a parse of 645 KB. So a plain relaunch reads nothing, a fortnight off reads a fortnight, and widening retention reads the whole window again. Deleting the archive ends a pass in flight and records the window as covered, because a pass is a second writer the aggregator's `forgetArchivedDays` does not reach — cancelling alone is not enough, since cancellation is observed between files. Measured on one machine: 419 Claude files and 424 Codex rollouts, ~870 MB, 73 s in a Debug build, and the archive it wrote agrees with `ccusage` **to the token on all four counts across 70 days**, both providers, with the whole cost within $0.00008 — the `pricing-oracle` job asserts that on a dated fixture, which `--scan` structurally cannot, since it runs the tail's own window and reports today.
- **A project is a repository, not a directory.** `ProjectResolver` walks up from the `cwd` a log line names to the first `.git`, and a `.git` *file* means a worktree whose `gitdir:` pointer names `<main>/.git/worktrees/<name>` — so the work counts against `<main>`. Without that one repository reads as several rows that each look small: measured on a real day, 44 distinct working directories resolve to 31 projects, and `sissy` only adds up to its real figure once its worktrees fold into it. `legion/frontend` is not its own project either. Two unrelated repositories sharing a basename render the same label and are told apart by the path in the tooltip — the accepted cost of a row named the way the user names it. **A walk that names no repository answers nothing**, and the usage is counted without a row rather than given one named after a path Sissy cannot verify: a CLI's per-conversation scratch directory is not a project, and neither is a deleted worktree, whose money belonged to the checkout it was cut from. The walk never stats the starting directory, so a worktree kept *inside* its repository still resolves once deleted. One kept beside it has nothing left to walk up to, which is why **a checkout a `.git` entry has been read from is remembered**, and why what remembers it is `ProjectLedger` rather than the tail's snapshot: it holds no token math, so a `UsageStateSnapshot` schema bump must not take it — that bump quarantines the file and forces the cold scan that needs the memory most, and it has happened seven times on one machine. It is **one ledger for every provider**, because two answer the same deleted path differently as soon as one has seen it alive: as a memory per adapter, Codex's held nothing at all, none of the directories its own rollouts name being a repository. `projectCheckouts` stays on the snapshot read-only, so an install that predates the ledger hands its memory over once. **The ledger learns from git, not only from the lines it reads**: landing on a repository reads the worktree list git keeps in `<repo>/.git/worktrees/*/gitdir`, at launch and on the tail's own cadence, so a worktree is written down while it is alive instead of looked for once it is gone. Without that, learning is a race against `git worktree remove` that the tail loses whenever it is not running — measured 2026-09-13, a cold read of that day's logs could name 66% of its tokens and the day before 21%, every missing one belonging to a worktree already deleted. What none of this can answer for is a checkout created *and* deleted while Sissy was not running: git has pruned its side, the logs name the path and nothing else, and there is no reading left to remember — **unless the session wrote it down itself**. That is the `checkout-inbox`, fed by the `SessionStart` hook `AgentHookInstaller` registers with both CLIs when the user switches it on, and it is the only evidence that does not require Sissy to have been running. `session-start.sh` reproduces the walk exactly: `--show-toplevel` for the checkout, the common dir minus `/.git` for the repository, a submodule answering itself. Two guards are not optional and were both measured: an inherited `GIT_DIR` beats `git -C` and answers for a repository the session was never in, so the environment is stripped; and `core.worktree` lets a repository name any path on the machine as its own checkout, so the toplevel must be the directory the session started in or an ancestor of it — which is the invariant the walk gets for free. The inbox is foreign input and is read as a boundary: `O_NOFOLLOW`, a regular file this user owns, size-capped, two absolute lines, and `adopt`ed rather than `remember`ed so what Sissy saw itself always outranks what it was told. An entry is consumed on read, which is what bounds the directory. What is still unanswerable is a checkout created and deleted while *neither* Sissy nor a session was there. Remembering a reading is not inventing one: nothing remembers a directory no `.git` was ever read from, so a CLI's scratch directory stays nameless however often it is seen. A directory still on disk is answered by the disk, because an emptied directory is a change in what a path means where a deleted one is the end of it. Without this, attribution is a property of when Sissy happened to read the line rather than of the work — measured 2026-09-13, the live tail named 99.7% of one real day and a cold re-read of the same day after its worktrees were deleted named 34%; across the whole history 23.3% of tokens no longer resolve, and 50.8% of September's, the month ephemeral worktrees became how the work is done. That is also what stops a cold scan from *degrading* a day the live tail attributed correctly, since a row it can no longer name goes unattributed instead of moving the money to a dead path. **A project path a persisted row carries is read through the resolver again before it is used**, never migrated on disk: the archive keeps the directory it saw, and what that path *means* is today's answer — for a checkout that is gone, the repository the remembered reading named; for a path no reading ever verified, nothing at all, so a row an older build wrote for a scratch directory stops claiming one. Two rows that answer the same key sum rather than replace. Rewriting the file instead would destroy the attribution of a repository on an unmounted disk the first time it is read without it, where a projection answers from the checkout it remembers and is whole either way. It is also what lifts the freeze the coverage check would otherwise hold such a day in forever. **A project path is personal data** — a client's name is a directory's name. The panel renders the last component only, the archive holds the path, and anything that carries it off the machine has to say so. `UsageHistoryExport` is the one thing that does: it writes both the label and the path, because a pivot table that groups on the label alone sums two repositories sharing a basename into one row, and the button that writes it names what the rows carry before it is pressed rather than after.
- **Settings has a height budget, and a row shape that pays for it.** `SettingsRootView.maxContentHeight` is 600 pt: a tab that needs more scrolls, and a tab that habitually needs more is a tab that should have split. Without a ceiling the window followed its content off the bottom of the screen and there was no way back — `fixedSize` is what makes the window follow the selected tab, and it also makes it unresizable and stops the `Form` underneath from ever scrolling, since a scroll view given its own ideal height never compresses. Measured: General at 850 pt against the 841 pt a 14" Mac set to a larger text size has room for, and the 775 pt of a 1280×800 display. What buys the room is the row — every control is a `LabeledContent` whose label carries the title *and* its description, so the caption sits beside the control instead of under it as a full-width paragraph, and the platform words it as secondary rather than one point below the label. Measured on the same eight controls: a `Section` per control with a `callout` paragraph came to 779 pt of content, this shape to 471 pt. **The prose was never the problem and deleting it is not the fix** — the ⓘ popovers are where a control that reaches outside Sissy's own folder says so before it is used — what the hook switch writes, and what the export carries off the Mac — the Files row still names both files, and the keep-awake caption still carries the only two numbers in the app that say when a hold ends. **A tab is earned by a module, not by a long tab**: #38's notifications pane is a tab, a pane holding one switch is a row.
- **One Sissy, two poses.** `SissyModel.sissyAssetName` is the resting silhouette; `sissySleepingAssetName` is the same silhouette with its eye shut, and it is what the menu bar *and* the panel header rest on while nothing is reaching the app. Both are template images, so surfaces tint them and never ship a second copy. The icon is drawn at full opacity in both states — the shut eye replaced a 40% dim, so don't reintroduce one. Sizing is per-surface: the menu bar draws it at 17 pt because the asset carries 20 pt of ink where an unconfigured SF Symbol measures 15, and at native size it reads a third taller than its neighbours. Copy the image before resizing — `NSImage(named:)` returns the catalogue's shared instance.
- **Sissy's motion is one 24-frame sequence.** `Assets.xcassets/SissyMotion` holds a blink rendered at 60 fps as vector imagesets, and `SissyMenuBarMotion` slices it into the whole blink plus its two halves. Frames 6–9 are the byte-identical shut-eye hold, which is why the closing half stops at 6, the opening half starts at 9, and `step(at:)` reports the hold as a single frame held for all four frames' worth of time — a write to `button.image` is answered by AppKit re-capturing the whole status item into a bitmap (`NSStatusItem._updateReplicants`, measured at 34% of the app's idle main-thread work), so a frame nobody could tell from the last one is not free. `SissyMenuBarAnimator` owns `button.image` from the moment it exists — anything else assigning it drops the remaining frames of a gesture. A blink fires when a frame lands (`SissyModel.lastFrameAt`, rate-limited by `SissyMenuBarMotion.dataBlinkCooldown`, because the tail coalesces emits only down to `UsageReaderShared.pollEmitThrottle`); the halves play when the pose changes; Reduce Motion, an open menu, or the pose the app launches in snap instead. **Two surfaces play Sissy**, and they are separate implementations because one assigns an `NSImage` and the other is SwiftUI: the status button through `SissyMenuBarAnimator`, and the panel header through `Panel/PanelSissy.swift`, which blinks on the same arrivals so an open popover is not a still Sissy. What they must not each reinvent is the timing — `SissyMenuBarMotion.step(at:)` is the single source of which frame a running gesture is on, and `dataBlinkCooldown` of when the next one is due. The panel plays only the blink: the poses still cross-fade there, since a 24 pt SwiftUI `Image` swap has no menu bar to match. There is no idle animation and no gesture on the cost axis: motion reports arrival, not spend. The frames are derived art — regenerating them needs the motion geometry that lives outside this repo, so a re-traced silhouette means re-rendering all 24.
- **A row answers for itself in a menu, and a block too long for a row answers in a page of the panel.** Two surfaces used to answer in a nested `.popover` — `ProjectRowView` and the status block's service tree — and as of 0.1.10 neither does. Apple's guidance rules it out in one line: *"Never show a cascade or hierarchy of popovers, in which one emerges from another"* (Human Interface Guidelines, Popovers). The cost of ignoring it was measured, 2026-09-17 on macOS 27 against a harness reproducing `UsagePanelController` exactly: dismissing a popover presented from inside the panel leaves the panel's own window with its new size committed to the window server and its **new origin not**, for ~555 ms. Cocoa origins are bottom-left, so for that half second the panel held its bottom edge and moved its top, drawing itself displaced by exactly the height difference between the page it left and the page it arrived at — down when the destination is taller, up when shorter, and the header off the top of the screen either way. `NSWindow.frame` was correct throughout, so nothing in this app's layout could see it or fix it, and every remedy measured failed: `animates = false`, resetting `backingType`, `disableScreenUpdatesUntilFlush()`, `setFrame(_:display: true)` with `invalidateShadow()`, nudging the origin, resetting `positioningRect`, and deferring the resize by 16, 50, 120, 250, 300, 350, 400 or 500 ms — the freeze ends at a fixed moment whatever happens in between, so a later resize is simply wrong for less of it. Not resizing inside that window is the only thing that works, and a surface that is not a popover never opens it. So the tree is a page (`UsagePanelView.Page.services`, one level in from the vendor's own), which also answers the complaint the card was invented for better than the card did: nothing below it can be pushed, because there is nothing below it. And the repository's row carries the **forge's mark after its name, and the mark is the link**: it costs the row no height, a row without one is saying there is nothing to open, and a mark placed *before* the name would start every repository's name one step right of every other row's — which is the rule the bars were given a line of their own to keep. A pull-down `Menu` was tried in between and dropped: it opened over the rows below it, which is a lot of a 340 pt panel spent on two items, and macOS draws no icon in a SwiftUI menu item, so the mark had nowhere to be inside one. The two actions — the page, and the path on the clipboard — sit on the **right-click**, which is where the same guidance puts them: *"a context menu lets people access a small number of frequently used actions relevant to their current view or task"*. A menu is the system's own mechanism rather than a window of Sissy's, so it cannot resize the panel and does not dismiss the popover it opens over, measured on macOS 27. The hover stays the tooltip's, which is the only place a path is readable, and a path the pointer could select is what this gives up — so it goes where selecting it was heading, the clipboard. What neither surface may ever be is the only way to something: the repository's own name stays on the row and its path stays in the tooltip. The page it offers is **read rather than guessed**: `ProjectResolver.remote(ofRemoteURL:)` keeps a remote a browser can already open exactly as it is, port and all, and composes `https://<host>/<path>` only where the host is the whole address — an `ssh` remote naming a port is pointing at a transport, `ssh.github.com` on 443 serves no page, and that row keeps its repository with no way out to it.

- **The panel's ceiling is the screen it opens on, and no section pays for it.** `UsagePanelController` reads `button.window?.screen` per showing and hands `PanelMetrics.maxHeight(on:)` to the panel, which measures its header and its page and gives the page's scroll view the smaller of its own height and what is left. A page that fits is untouched — the scroll view is set to the page's measured height and scrolling is disabled — so the popover is the size it has always been. This replaced a ceiling on the project list, which was the wrong trade: measured 2026-09-15, `visibleFrame` is about 957 pt on a 14" built-in and 1415 pt on a 2560×1440 external against a tallest-page reading of 690.5 pt, so the section was hiding repositories to fit a screen nobody was in front of. Bounding a section is for keeping what is *below* it reachable, or a page from being one click away from several times its own height — the second is what `StatusTreeGeometry` still does for 34 OpenAI components — never for keeping the popover on the display. **Two mechanics here are measured and not guessable.** A `ScrollView` is greedy: given a flexible proposal it takes all of it, so `.frame(maxHeight:)` on the panel, `.fixedSize` on the scroll view and both together all report the full ceiling for a 100 pt page. Only an explicit height on the scroll view works, which is why the ceiling cannot be expressed on the panel as a whole — the greedy child is what it would be clamping. And a height measured with `onGeometryChange` is not available to the layout pass that produced it: the first `sizeThatFits` answers with the header alone, so the controller lays the host out before `show`, or the popover opens as a 45 pt stub and jumps.
- **A surface that is not on screen costs nothing.** `UsagePanelController` builds the panel's `NSHostingController` when the popover opens and drops it in `popoverDidClose`. A closed popover keeps its window, and a host left attached to it keeps a live SwiftUI view graph inside it: `SissyModel` is `@Observable`, so every frame the engine emits bought a layout and a full rasterization of all 340 pt of the panel into a backing store nobody could see, and `PanelSissy` turned each arrival into 23 of those at 60 fps. Measured on macOS 26 against a Debug build, panel closed and the app otherwise idle: **8.7% of a core before, under 2% after** — the main thread alone went from 15% to 1.1%, and 79% of what it had been doing was inside `CA::Transaction::flush`. The rule generalises past the panel — anything that grows a retained host must stop observing when it is not visible, and `sample <pid>` is how you tell.
- **Sissy binds no port, and reintroducing one is a new design.** The server, the bearer token and the 5155/8787 port existed so an ESP32 on the LAN could pull frames. There is one consumer now and it is in the same process. If a second one ever appears — a widget, a CLI reading live state — that is a new decision with its own design, not a revival of the socket.
- **The git tag is the only version source; never hand-edit a version.** `scripts/version.sh` resolves `MARKETING_VERSION` from the latest tag and `CURRENT_PROJECT_VERSION` from `git rev-list --count HEAD`; `release.sh`, `release.yml` and `dev-build-app.sh` pass both to xcodebuild, which reaches both targets in one build. Cutting a release is `git tag -a vX.Y.Z && git push --tags` — there is no bump commit. The pair in `app/project.yml` is a `0.0.0` / `0` dev placeholder, and both `Info.plist` files carry only `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)`. Reintroducing a literal in either plist recreates the bug where 0.1.6 and 0.1.7 both shipped build 6; the pre-notarization `verify bundle version` guard in `release.sh` and `release.yml` exists to catch exactly that. The release workflow needs `fetch-depth: 0` — the default shallow clone makes the commit count 1.
- **There is no hand-maintained rate table, and adding one is a regression.** Rates resolve through three sources: `server.json` `pricingOverride` → the LiteLLM catalog fetched at runtime (`PriceCatalog`, refreshed every 24 h, cached in Application Support) → `PricingSeed.swift`. A provider shipping a new model therefore needs **no Sissy release**. If a model prices at $0, fix the seed or wait for the refresh — do not reintroduce a table.
- **`PricingSeed.swift` is generated, not authored.** Regenerate when cutting a release: `sissy-cli --dump-seed > app/SissyCore/PricingSeed.swift`. It is produced by the same Swift parser that validates the runtime fetch, so there is no second implementation to drift.
- **ccusage is the cost oracle — specifically whatever `npx ccusage@latest` resolves to.** It prices from LiteLLM too, so reading LiteLLM directly is what keeps Sissy agreeing with the number users cross-check. Where the two would disagree, match ccusage — subscription users never see a token invoice, so agreeing with the community tool beats agreeing with a hypothetical bill. The `pricing-oracle` workflow asserts exact agreement on a synthetic fixture, and invokes it as `npx ccusage@latest`. Verify pricing questions by **measuring** against ccusage, not by reading pricing pages: two independent readings of the long-context rules (an earlier pass here and a Codex review) both got them wrong, and a three-point measurement settled it in minutes.
- **The divergence is a version, not a package manager.** npm no longer ships the JS implementation: at 20.0.20 the `ccusage` package is a launcher whose `src/cli.js` spawns `@ccusage/ccusage-<platform>`, a native binary of the Rust rewrite — verified 2026-09-12 (`file` reports Mach-O arm64). So "the npm JS build" and "the Homebrew Rust build" are no longer two implementations to choose between, and the old framing of this rule was wrong. What is real is the **stale pin**: measured on 1M `ephemeral_1h` opus tokens, build **20.1.0** bills the 1-hour tier at the 5-minute rate and says $6.25 where Sissy says $10.00 (2026-07-29 and 2026-09-10), and **20.0.20 says $10.00**, agreeing with Sissy (re-measured 2026-09-12). Claude Code writes ~93% of its cache at the 1h TTL, so a 20.1.0 reading looks like Sissy over-billing by ~7% — it is not. The trap that keeps 20.1.0 alive is Homebrew's: the project moved from `ryoppippi/ccusage` to `ccusage/ccusage` and renumbered *backwards*, so `brew outdated` sorts 20.1.0 above 20.0.20, stays silent forever, and `brew upgrade` is a no-op — only `brew uninstall ccusage` and a fresh install move it. Before acting on a user-reported gap, get their `ccusage --version`; About → **Copy diagnostics** also names the install (`CcusageProbe`, which classifies it by where its symlinks land — `node_modules` is npm, `Cellar` is Homebrew).
- **A stale `brew` ccusage will never upgrade off itself.** The project moved from `ryoppippi/ccusage` to `ccusage/ccusage` and renumbered *backwards*: the old formula pinned v20.1.0, the current one v20.0.20. Homebrew sorts 20.1.0 as newer, so `brew outdated` stays silent forever and `brew upgrade` is a no-op — a machine that installed it before the move keeps serving the build with the cache-write bug. Only `brew uninstall ccusage` and a fresh install move it. The fix that removes the whole class of confusion is `npm i -g ccusage`, which puts the oracle itself on `PATH`. Note the 1-hour bug is fixed in the current Rust source (`CACHE_CREATE_1H_INPUT_MULTIPLIER = 2.0` in `ccusage-core/src/cost.rs`), so the divergence is version-specific — but that same file bills long context as whole-request substitution where the JS was measured to bill only the tokens above the threshold, so the two implementations still are not interchangeable.
- **A repeated assistant line is a turn still streaming, not a duplicate to drop.** Claude Code writes the same `requestId` two to four times as an answer streams: `output_tokens` grows with each copy while the input and cache counts, fixed when the request was made, repeat unchanged. `ClaudeCodeAdapter` therefore bills a repeat as the **difference** in output and nothing else — `SeenEvent.billedOutputTokens` is what the dedup ledger carries for it, and `UsageStateSnapshot.DedupKey.outputTokens` is why a turn whose copies land either side of a relaunch is still billed once and whole. Measured 2026-09-12 on 2026-09-11: keeping the first copy gave opus 2 751 478 output tokens against ccusage's 2 872 151 and the day $3.97 short, while keeping the last lands on **all four token counts exactly** for both models and the day within $0.000022 of $598.854905. This replaces an earlier note claiming a ~0.35% residual localized to `isSidechain` sub-agent entries: sidechains had nothing to do with it, dedup policy had nothing to do with it either — deduping by `requestId`, by `message.id`, by the pair, per file or across the tree all give the same number. The oracle fixture carries a four-copy turn for this reason; a fixture of one line per request id bills the same either way, which is how the bug shipped past it.
- **Long-context tiers are deliberately not modelled.** Some models publish an above-200k/272k rate. ccusage bills only the tokens *above* the threshold (measured, not inferred — Anthropic's published table reads as whole-request substitution, so ccusage is arguably wrong). Claude Code compacts before reaching the threshold, so the case is near-unreachable; it was implemented once and removed as unjustified complexity.
- **The plan comes from a different place for each provider, and in neither case the obvious one.** Codex names it on the same `rate_limits` block as its windows (`plan_type`), so `captureWindows` takes both and `codexResume.plan` persists it for the same reason it persists the windows. That source answers only while there are unread bytes, though — a reader resuming with its offsets at EOF has nothing left to re-read and the row sat without a badge until the user's next turn, so `CodexAuthSource` reads the `chatgpt_plan_type` claim out of the id_token in `~/.codex/auth.json` at boot and any rollout event then overwrites it. Measured the same day: an account archived before `seat` existed kept badging "Team" beside a live "Team Premium", and would have kept it through a fresh link. Downstream of that, a row resolves **one** account rather than ordering field by field — the reading's, and the archive only where there is no reading at all — which is safe precisely because the reading is already attributed to the row it is on. Every token reaches the app raw and lowercase; `UsageFormat.plan(_:tier:)` is what words them, so a tier a vendor ships tomorrow needs no release. Neither *file* is fresh on demand: Claude's updates when the CLI re-fetches its profile, and Codex's id_token is restamped only when the CLI renews it. What answers on demand is the usage endpoint each vendor publishes, which names the plan beside the windows — so the badge is one poll behind rather than one turn. **That same file answers for the credits, and it is a record rather than a reading.** `cachedUsageUtilization` in `.claude.json` is the usage endpoint's own reply, cached by the CLI — the identical payload `ClaudeLimitsProbe` authenticates for, `spend` block and all — so the number someone opens the browser for is readable with no prompt, no network and no grant to lapse. **What it is not is current, and it cannot be made current.** Measured 2026-09-14: the CLI rewrote `.claude.json` ten seconds before the reading and `fetchedAtMs` had not moved in 59 minutes of continuous Claude Code use, because only `/usage` refreshes it. Against the live reply at that moment it named 19 260 credits spent where the account had spent 26 275, under a cap it did not know had been raised from 25 000 to 30 000. So it is the fallback when nothing better is running and never an argument against a live source — an earlier version of this note had it the other way round and was wrong. Hence the reading carries the vendor's `fetchedAtMs` and the panel prints it: a spend shown without its age is a claim of being live that this source cannot make. The money stays in minor units with the vendor's own currency and exponent all the way to the formatter, and never meets `ProviderSlice.cost`: one is what was charged, the other Sissy's estimate of what was metered, and summing them would be inventing a third number. **And it answers for an account that is not necessarily the one signed in.** Only Claude Code writes that file, so a switch Sissy makes reaches the keychain at once and `.claude.json` not at all — measured 2026-09-16, a switch at 16:26:53 left a file rewritten at 16:29:31 whose `oauthAccount` had been fetched at 12:28:10 and had not moved, so the row carried one account's id under the previous account's name, email and seat, and switching again could never change it. The file names its own owner and Sissy reads it: `oauthAccount.accountUuid` and `cachedUsageUtilization.accountUuid`, **two stamps rather than one**, because the blocks are written at different moments and legitimately disagree — a running `claude` holds its identity in memory, so that same day's usage cache was refreshed 39 s *after* the switch and still stamped with the account it had started as. `ClaudeCodeSignals.attributed` therefore judges each half against the registry's active account: an identity that contradicts it gives way to the registry's, credits that contradict it come off the row, and agreement keeps the file whole, because it is the richer reading and the only one that names the seat. Unknown on either side is not a contradiction — an older CLI writes no `accountUuid`, and a registry that has identified nobody claims no active account — and the reading stands as it always has. The registry can lag too, by its 120 s poll and indefinitely while `identify` is offline, and it is still the authority here: the row is keyed by `activeUUID`, so pairing it with that account's own identity is one account per row, which is the invariant, where the file's was two. **And where the registry names nobody, the file's own stamp is the active account.** The registry names nobody whenever it has never identified a credential — offline at launch, a keychain that would not answer, an engine built without one — and that state used to stand every judgement down: a lone claude.ai session was laid over the row whoever it belonged to, and a `cachedUsageUtilization` stamped with another account was kept. `ClaudeCodeSignals.activeAccount` is the one answer all three readers take, so a name is available wherever one exists. The exception that survives is a Mac nothing names at all, where a lone session is the only answer there is.

- **A credits reading is the vendor's own figure in the vendor's own unit, and three absences are not zero.** Anthropic bills a spend against a cap in the account's currency; OpenAI writes a credit *balance* on the same `rate_limits` block Sissy already parses for the windows and the plan, names no currency for it and sends `individual_limit: null` — measured 2026-09-16, on all 10 306 blocks on one machine. So `ProviderCredits` carries a `CreditsUnit` and every figure on it is optional: a source answers for what it can and says nothing about the rest, and folding those together invents a number. **What this buys Codex is a line, not a gauge** — with no ceiling a bar would be picking a denominator the vendor did not give, which is the one thing this row exists not to do, so `CreditsRow.fraction` is optional and the bar goes with it. The two ways the reading goes missing are two different facts and neither is zero: the key is absent on a Codex older than 2026-05-18 (6 801 blocks), and `balance` is null where the CLI has the key and not the figure (23). **Neither flag beside it is read, and the omissions are the same rule read from both ends.** `unlimited` suppressed the whole reading for one build, which was inventing an absence: it only means an *absent* balance is not worth reporting as missing, and a balance that does not parse already answers nil on its own — CodexBar reaches the same place from its own measurements, keeping a finite balance or cap reported alongside the flag and dropping only the reading that names neither. `has_credits` is deliberately **not** read as `isEnabled` — it reports whether a finite pool exists, and `has_credits: false` beside `balance: "0"` is the ordinary reading on an account that never bought any, which is 3 482 blocks here and the confirmed zero the row prints. The balance arrives as *text*, so it is shape-checked before parsing and read against `en_US_POSIX`: `Decimal(string:)` takes the machine's separator and answers with however far it understood, which on this Mac turns `"12.5"` into `12` and `"12 credits"` into `12`. It rides `codexResume` for the reason the plan does — with offsets at EOF there is nothing left to re-read and the section would be missing until the CLI's next turn. What is still Claude's alone is the hidden zero: a spend of nothing against no cap gets no row, because that is most accounts and a permanent "Not enabled" under every provider page is a row that never changes.
- **A vendor's status is read from the vendor, dated by Sissy, and never inferred.** `ProviderStatusMonitor` polls each metering vendor's public status page so "is it me or them" costs no browser tab. Four things about it are settled and measured. **The age on the row is Sissy's own fetch time**, never the feed's `updated_at` — measured 2026-09-15, OpenAI's read `2026-07-09`, two months stale, because it moves on incidents rather than on polls; a row dated from the payload tells a healthy provider it has not been heard from since July. **A failed fetch publishes nothing**, so the last reading keeps its own age and the age growing is the signal; a feed that has never answered says `unknown`, which is never an outage, because a page Sissy could not reach is not an incident. **The sentence is one shape and the tree is two.** Both vendors answer Statuspage v2 at `api/v2/status.json`, so the row has one reader; the services under it do not. Measured the same day, OpenAI's Statuspage-emulated `summary.json` answered 25 flat components where its own page carries 34 in 5 groups — it drops eight, `Chat Completions`, `Responses`, `Conversations`, `GPTs`, `Image Generation`, `ChatGPT Work`, `Ads Manager` and **`CLI`**, which is the row a Codex user opens the tree for, and folds the two `Login` components into one. So Claude is read from `summary.json` at one request, and OpenAI costs a second to `proxy/<host>` for the tree. That is the one place this deviates from #84's "one request per provider per poll", and it buys the feature the issue defers to its follow-up. **The wording is the vendor's**: the sentence, the component names, their order and their nesting are all copied rather than composed, `only_show_if_degraded` and `hidden` rows are dropped because the page drops them, and a status token this build does not know prints humanised instead of blank. **The tree opens as a page of the panel**, not in place and no longer in a card. Expanding it underneath the line made it the one block on the page whose height a click changed; a nested `.popover` fixed that and cost the panel half a second of mis-drawn geometry on the next navigation, which is the note above. A page answers both — the provider page is the same height whether the services have been visited or not — and it needs no ceiling of its own, since `PanelMetrics.maxHeight` and the panel's own scroll view are what bound it, which is what replaced every per-section ceiling in the first place. The block still sits at the foot of the provider page, but the reason is now the question rather than the height: what a vendor says about itself is the least-asked reading there, and the alarm loses nothing by it, since a degraded vendor already colours its own name on the Overview. What is deliberately not here: incident history, which is what the link to the page itself is for, and any notification, which belongs to #38's per-alert switch.
- **Codex answers for more than one account, and the mechanism is a credential rather than a home.** The limits, the plan and the credits are all on `chatgpt.com/backend-api/wham/usage`, which answers 200 to a bearer token under any User-Agent — measured 2026-09-17, the same block the tail parses off `token_count`, live: the endpoint said 32% where the freshest rollout on that machine was 1 h 51 m old and said 30%. So `CodexUsageSource` is **one reader per credential**, and which account it answers for *is* which credential it holds. The CLI's own `auth.json` is one of them, built with no account of its own because which account that file holds is the CLI's to change; every other is an OpenAI sign-in the user made in `VendorLoginWindow`, filed in a keychain item of Sissy's own (`com.radonforge.sissy.codex-oauth`). **That is deliberately not CodexBar's `CODEX_HOME` per account**, which is the trade #130 rejected and has a defect worth naming: a plain `codex` uses the ambient home, so the extra accounts are the ones the user is not working in. Here nothing is written where a `codex` could read it, so linking an account cannot change which account the terminal is on — and unlinking one cannot either. Four things about it are settled. **The row key is the login, not the workspace**: `chatgpt_user_id`, which is stable across a refresh where the tokens are not, with the workspace recorded beside it in `codex-accounts.json` — a login holding two workspaces is metered twice and membership order is the server's, so the link asks once (`backend-api/accounts`) and records the answer, exactly as the Claude link does for an organisation. A workspace list that could not be read costs the row a name and never the login, because the credential already names the workspace OpenAI defaults it to. **Renewal is ownership**: `CodexCredential.refreshToken` is nil for every credential read from `auth.json`, so "Sissy never renews the CLI's credential" is a property of the value rather than a rule each caller has to remember — the token is one-time, and redeeming the CLI's would strand the terminal. Sissy's own copies it does renew, and files the renewal in the same breath, because OpenAI rotates the refresh token. **The two readings are settled by their stamps, not by rank**: `CodexSignals.merge` takes the later of the tail's and the reader's, which is self-correcting in both directions — a poll is newer than the last turn by construction, and a reader that has stopped hands the row back to the turns without anything having to remember which is preferred. **And the sign-in is the Codex CLI's own client id**, which is public by construction and in every `auth.json` on the machine. That is the one part of this that is a trade rather than a measurement: the alternative was spawning `codex login` against a home of Sissy's own, which needs the binary on `PATH` and shows the same page. What a linked Codex account does **not** get is a spend of its own — a rollout names no account, so the day belongs to the config home exactly as Claude Code's does — and no `Use in CLI`: Sissy signed that account in for itself, it never took the CLI's, and there is nothing to put back.

- **A config home is a place a CLI writes; an account is a credential.** Sissy reads one config home per vendor — `CLAUDE_CONFIG_DIR` / `CODEX_HOME`, or the default — and reports what that CLI spent. It does **not** attribute spend to an account, and cannot: a Claude Code `*.jsonl` carries `cwd`, `sessionId`, `requestId`, `userType` and no identity at all, so whoever was signed in when a line was written is not in the line. Requiring a home per account to recover that was the wrong trade — it is configuration a user never asked for, and a `claude` started with no variable writes into `~/.claude` whichever account is signed in, so the split does not even hold. What the account *does* decide is the identity on the row and the limits under it, both of which come from the credential. `ProviderHome` is the resolved paths of that one home; the one asymmetry it encodes is that with `CLAUDE_CONFIG_DIR` unset the config home is `~/.claude` but `.claude.json` sits beside it at `$HOME/.claude.json`. Attribution per account stays reconstructible later — `ClaudeAccountRegistry` already knows when the active account changes — without any of this coming back.
- **Claude's limits come from the CLI's own credential, and Sissy asks for no permission to read it.** `<home>/.credentials.json` holds the OAuth token in plaintext with scopes including `user:profile` — the scope #103 road 2 died for lacking — and measured 2026-09-15 it answers `api.anthropic.com/api/oauth/usage` with HTTP 200, live windows and a `spend` block. Where there is no file the same credential is in the login keychain, read through `/usr/bin/security`: a keychain item's ACL names *applications*, Claude Code files its item by shelling out to that tool, so `security` is on the ACL and Sissy is not. Measured the same day on macOS 27 from a process that had never touched the item, a read and a write both returned 0 with **no dialog**, where an in-process `SecItemCopyMatching` raises the legacy Allow/Deny panel and earns a grant that dies at the next token refresh. That is why there is no longer a "Show Claude Code limits" switch: it existed only to make that prompt expected, and there is no prompt. It also grants Sissy nothing new — any process running as this user can read those items the same way. Sissy never writes the CLI's credential except on an explicit switch, and never refreshes: Anthropic's refresh tokens rotate on use, so spending one would sign the user out of their own terminal. The ceiling is the access token's own life, so a CLI that has not run for hours shows no live limits until it is used again.
- **A live limits reader answers for the credits too, including when it has none.** `cachedUsageUtilization` in `.claude.json` is not invalidated when the CLI signs into a different account — measured 2026-09-15, a config naming an account created the day before still carried the previous account's spend, in the previous account's currency (€359.34 against a live $0). So `ClaudeCodeSignals.merge` takes the running reader's credits wholesale rather than letting the cached copy fill in behind a nil. The cache is the answer when nothing live is running, which is every user who never switched limits on, and never an amendment to one that is.
- **If Sissy switches accounts, Sissy owns the archive.** The CLI's keychain slots are **scratch**: the unscoped `Claude Code-credentials` and each `Claude Code-credentials-<sha256(NFC(configDir))[:8]>` hold whichever account is active, and the CLI rewrites them with a rotated token on every refresh. Measured 2026-09-15 the hard way — writing account B into the unscoped item let a `claude` on `~/.claude` adopt it, refresh it, and overwrite account A's only copy in its own scoped item *and* `~/.claude/.credentials.json`; refresh tokens rotate, so A was gone from the machine entirely and cost ≈$36 billed to the wrong org before anyone noticed. `ClaudeAccountRegistry` is the answer: it watches the active credential, asks Anthropic whose it is whenever it sees one it has not archived — a switch, a `/login`, or a rotation — and files a copy under that account's uuid in a keychain item of Sissy's own, with an index beside it that holds identities and never a token. An account becomes switchable the first time it is used on this Mac and stays switchable, with no directory, alias or variable to configure. What it cannot do is offer an account that has never signed in here; that first `/login` is the user's. This is a deliberate exception to "nothing Sissy does to the machine outlives Sissy" — it stores credentials and it writes the CLI's slots — and it earns it the only way it can: the switch runs from one click and nothing else, and nothing it holds reaches the frame, the logs, the diagnostics or the export. What it does **not** yet earn is a way out from inside Sissy. There is no control that deletes an archived credential and no code behind one — a `forget` chain was written ahead of its UI and removed unused — so the README names the keychain item and sends the user to Keychain Access. That is a debt against this rule, not a settled shape. **Unlinking is the session's, never the credential's.** The trash on a Settings row takes the claude.ai session and nothing else: that is the half the user added and the half Sissy can put back, one window away. The archived credential is the half Sissy took itself, and there is no second copy to make — `/login` mints one and it is the user's. Deleting it while the CLI is on that account leaves exactly one copy, in a slot the next `Use in CLI` overwrites, and refresh tokens rotate, so the account is off this Mac until a terminal signs it back in. A delete must not reset `lastSeenToken` either, or `captureActive` re-archives the still-active account on its next poll; leaving it alone means the CLI has to rotate first — 26–73 minutes measured — which is how long that single copy stands alone. Whatever eventually deletes an archived credential is therefore its own control with its own words, off `ClaudeAccountStore`'s list rather than `ClaudeWebSessionIndex`'s; the two lists have separate lifetimes for exactly this. **That trash asks before it deletes, and is drawn red.** A session is a secret the user cannot read back and never typed, so the one click that removes it is not a click to get wrong — measured the hard way on the dev build, pressed by accident on the account its owner was signed into, where nothing visibly changed because that account's limits were coming from the CLI's own credential anyway. "Cheap to link again" is a reason not to make the delete unrecoverable, never a reason to skip asking.

**The claude.ai session is the fallback for a Mac whose CLI keeps no credential file.** It led this list until the credential file above was measured, and it is kept because that file is Claude Code's and a Mac may not have one. `VendorLoginWindow` signs in at claude.ai once — on the click, never on a poll — and the session is filed in a keychain item Sissy owns (`ClaudeWebSessionStore`); `ClaudeWebSource` then polls `claude.ai/api/organizations/{org}/usage` for the windows *and* the credits, and an imported session is what decides which of the two *shared* readers runs, once the credential file has answered for nothing. **A sign-in rather than a copy of somebody else's**: the import that preceded this read Claude.app's cookie store, which measured well — Claude.app held a `sessionKey` good for four more weeks where Chrome's had expired three and a half months earlier and Safari held none — but it could only ever produce the one account that app was signed into, which is the whole of what #167 needed more than one of. What survives it is the item: a session Sissy owns, not a copy it keeps re-reading, where `Claude Code-credentials` is rewritten every token refresh. That is the whole difference from #103. Three things about the wire are measured and not guessable: the `Claude/<version>` product token in the User-Agent is what gets past the edge (a plain Chrome agent is 403, and `Electron/` does not substitute), the plaintext carries 32 bytes of Chromium domain-binding hash in front of the value, and an account can hold several organizations — the subscription is the one whose `capabilities` name `chat`, never the first one listed. The cookie is a whole claude.ai session, not a read-only usage token: it is never logged, never on the frame, never in the diagnostics or the export, and `ClaudeWebSessionSecrecyTests` is what holds that. **The sessions are the record, the links are a naming, and any list of accounts reads the record.** `UsageEngine.store(session:as:)` files the session and then tries to name it, catching a failed `remember` and keeping the session — losing a login to a disk error is worse than deriving an organisation — so a session with no entry is a state the ordinary path produces, and its reader polls claude.ai either way. `hasClaudeWebSession` and `rebuildClaudeWebSources` already answer off the stored sessions; a Settings list that read the links instead left one of two stored sessions with no row and no way to stop it, measured on the dev build 2026-09-16. `ClaudeWebAccount.list` is the join, driven by the sessions: the link names an account, failing that the account archive, failing that its own uuid — a poor label and the only honest one, and a row under it is what makes that session removable at all. The holding key is not an account and gets no row, for the reason no reader is built for it.
- **Codex writes more `token_count` events than there are turns, in two ways, and `last_token_usage` alone cannot tell.** The per-turn block is the right field (see the convention below) but not the whole question — *whether this event is a turn at all* is answered by what surrounds it. **`total_token_usage` is the authority on the first way**: Codex re-emits the previous turn's block verbatim when a session ends or is interrupted, leaving its own running total untouched, so an event whose total has not moved since the last one carries nothing new. Compare the block field by field rather than the one scalar — two readings whose totals match by coincidence while the breakdown moved are a turn. **A session's own `session_meta` answers the second**: one opened from another — a forked conversation (`forked_from_id`) or a spawned subagent (`source.subagent.thread_spawn.parent_thread_id`) — writes that parent's entire history into its own log at creation, every copied event stamped within a millisecond or two of the session's start where a turn it actually ran takes seconds to come back. `CodexAdapter.replayedTurnWindow` is that separation, and it is a band rather than an edge: measured across a year of rollouts, anything from 50 ms to 3 s reproduces `ccusage` exactly, and 1 s is both the middle of it and ccusage's own constant. The gate on the parent marker is not optional — applied to sessions that copied nothing it takes real turns off the day, measured on two. Both rules are deliberately per-file: ccusage instead reads the *parent's* rollout to recognise the copy, and a tail that opens a second file to understand the one in front of it is a different design. Both pieces of bookkeeping therefore ride on `codexResume.fileModels` (`cumulative`, `copyingThrough`), because the repeat lands after the turn it repeats and a relaunch can fall between them. Measured 2026-09-14 before the fix: **1.8% over a year, 12% of July 2026** — a session forked three times replayed the same history three more times — and 4.5% of that day. With both rules Sissy lands on `ccusage codex` exactly, to the token and the microdollar, across all 55 days it has data for. The `pricing-oracle` fixture carries both shapes for the reason it carries a four-copy Claude turn: a rollout of one `token_count` per turn bills the same either way, which is how this shipped past it. A fork in that fixture has to be causally coherent — one that copies a turn its parent had not taken yet is a log Codex could not have written, and the two tools legitimately disagree on it.
- **Codex token convention.** `CodexAdapter` uses `last_token_usage` as the per-turn delta (verified against real rollout files — summing `last_token_usage` across events equals the final `total_token_usage` cumulative). `output_tokens` is treated as **gross** (it already includes reasoning); `reasoning_output_tokens` is a sub-breakdown of it that nothing reads — adding it to output would bill the same tokens twice. Verified on real rollouts: `total_tokens == input_tokens + output_tokens` regardless of `reasoning_output_tokens`. Same convention ccusage uses, so the two should agree within rounding.
- **A provider is named in nine places, and every one of them already has a default.** Adding one is a checklist rather than a refactor: `ProviderID` (`ProviderReadiness.swift`); its data-dir field and `ProviderToggles` with its subscript (`ServerConfig.swift`); `AccountDefaults.home`/`dataDir` and `ServerConfig.providerHome` (`ProviderAccounts.swift`); the construction arm in `UsageEngine.init`; `FrameBuilder.providerSortOrder`; `UsageFormat.providerName`; `ProviderPalette.tint`/`mark` plus the imageset; `ProviderStatusFeed.published`; and the `--scan-provider` arm in `main.swift`. `UsageEngine.persistenceURL` is deliberately not on the list — every provider but Claude Code already takes a file named after its own id. **None of the nine fails on an id it does not know** — the sort falls to `2`, the mark falls to a tinted dot, the tint to `.secondary`, the status feed to no row, the toggle to `nil` — so a provider that has only its adapter and its id renders as a plain row and counts correctly. That is what makes a registry unnecessary at two providers and cheap to justify at four: #35 designed one, and the measurement that deferred it is that the duplication it existed to kill was in the *readers*, which #68 already collapsed into `LocalUsageProvider` + `SourceAdapter`. Build the registry when a third provider has shown what a manifest entry must carry — the candidates surveyed in #35 each break a different assumption a Claude-plus-Codex manifest would bake in (Grok prices from the log line, OpenCode spans vendors and is not a byte-offset tail, Gemini is not append-only), so one designed today would be designed twice.
- **A provider switched off is a new engine, not a mutated one.** `UsageEngine`'s lifecycle is terminal — `stop()` cannot be undone — so `UsageEngineHost.setProvider` persists through `UsageEngine.setProvider` and then tears the engine down and builds another from the file. It costs what a relaunch costs, which is nothing: every reader resumes from its own snapshot's offsets, so no tree is re-scanned and no day is counted twice. Three things ride on that rebuild and are not optional. The frame on screen is **cleared**, because it still counts the provider that was just switched off and a panel that goes on showing it reads as a switch that did nothing. The agent hooks are **not** re-affirmed — `start(isLaunch:)` is that distinction — because those are lines in two other programs' configuration files and a switch flipped in Settings has no business rewriting them. And the row is shown thrown **before** the rebuild rather than after, because tearing an engine down flushes every reader's offsets first and the switch would otherwise sit in its old position for the length of that flush. What a switched-off provider keeps is its snapshot and its archive: retention is the engine's and bounds the days of a provider it never built, so switching one back on resumes rather than cold-scans.
- **Per-provider persistence.** The Claude Code provider writes `usage-state.json` (legacy path) for upgrade smoothness; the Codex one writes `usage-state-codex.json` via `UsageStatePersistence.forProvider("codex")`, and every further account takes a file named by its own key. A schema change in one provider can quarantine its snapshot without invalidating the other.
- **Adding a snapshot field: reach for an optional, not a `schemaVersion` bump.** `UsageStateSnapshot` is shared, so bumping the version discards *both* snapshots — measured 2026-09-10, that costs Claude Code a ~16 s cold scan of `~/.claude/projects` for a change that may tell it nothing. An optional field lets only the adapter that needs it treat `nil` as "cold-scan my own tree" (~2 s for Codex); `codexResume` is the worked example. Bump the version only when the change alters how a token count or cost is *derived*, which is what the field is documented for.
- **Codex resume state is not an optimisation.** `codexResume.fileModels` exists because rebuilding the per-file model map means re-reading every byte already consumed, and the reader emits nothing until it finishes — measured at 110 s on a 43 MB tree, during which the panel has no Codex row at all. `codexResume.rateLimitWindows` exists because the tail's own reading of the limits arrives only on the CLI's `token_count` events: with offsets at EOF there is nothing to re-read, so without persistence the tail has nothing to say until the next turn. It is still what answers on a Mac that is offline, on a token that has expired, and in the moment after a relaunch — which is why it is persisted and why **`CodexUsageSource` did not replace it**. What that reader retired is the *ceiling*: "always one Codex turn behind" was true for as long as the turns were the only source, and it was never a property of the vendor.
- **A docstring's measurement carries its date, and the symbols it names are checked.** A dated claim cannot become false, only irrelevant — `measured 2026-09-16` is what licenses a docstring to carry `137.5 pt` at all, where the same figure undated is read as present tense and eventually lies. A symbol name is the other half and the more fragile one: a number is self-contained and a wrong one is visible, while a name is a coupling to another part of the tree that breaks silently when that end is renamed. `scripts/check-doc-refs.py` takes every backticked identifier out of the `///` lines and fails on one the source no longer declares; platform APIs, environment variables and vendor names live in `.docref-baseline`, regenerated with `--write-baseline` the way swiftlint's is. Measured 2026-09-17 across 153 files: 551 distinct symbols cited in 987 mentions, and **two** stale — `limitsEnabled`, for the Settings switch that went with the keychain prompt, and `selected`, a `make` parameter dropped in 6f22fe2. Both had survived every reading of those files; neither survived the check.
- **Sissy links nothing third-party, and `CREDITS.md` is not a licence file.** The last dependency was SwiftNIO, which the WebSocket server needed; with the server gone the app ships only its own code, so nothing has to travel with the binary and nothing is bundled for it — `AboutTests` fails if a licence file reappears as a resource. `CREDITS.md` at the root credits the projects Sissy *reads* (`ccusage`, LiteLLM), which is courtesy rather than obligation, and About's Acknowledgements sheet lists the same two inline. Adding a dependency means putting the notices back, in both places.

## Local fast feedback (pre-commit)

`pip install pre-commit && pre-commit install` once per clone. Subsequent `git commit` automatically runs `swift-format`, `swiftlint`, `check-doc-refs.py`, `shellcheck` and `actionlint` against changed files. Same tools as CI, no version drift.

`pre-commit run --all-files` runs the full sweep.

CI lints against a recorded backlog in `.swiftlint-baseline`, so only **new** violations annotate a PR. Regenerate it from the repo root when the backlog legitimately changes (e.g. after a refactor that adds or clears violations): `swiftlint lint --write-baseline .swiftlint-baseline`.

## Quality gates

Consumed by the `/commit` skill. Run before each commit; `--no-checks` to skip.

```yaml
quality-gates:
  format: xcrun swift-format lint --recursive --strict app/Sissy app/SissyCore app/SissyTests
  lint: swiftlint lint --quiet --lenient && shellcheck scripts/*.sh app/Sissy/Resources/*.sh
  docs: python3 scripts/check-doc-refs.py
```

`test:` is intentionally omitted — `xcodebuild test` is too slow per-commit; CI catches it.
